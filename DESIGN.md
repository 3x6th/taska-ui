# DESIGN.md — Taska Design System

Единый источник правды по визуалу и поведению UI Taska. Этот файл читает и человек, и агент
(Claude Code / harness) перед тем как писать или менять UI. Если код расходится с этим файлом —
прав файл; если файл устарел — сначала обнови его, потом код.

**Стек-агностично.** Значения даны как CSS-переменные и числа, чтобы лечь в CSS Modules, Tailwind
(`theme.extend`), styled-components или vanilla CSS.

---

## 1. Design principles

1. **Тихий интерфейс.** Хром бледный, контент — контрастный. Цвет несёт смысл (тип, приоритет,
   статус), а не украшает. Максимум один акцент на экране.
2. **Воздух вместо линий.** Разделяем пространством и очень слабыми бордерами (8–9% альфы),
   не жирными рамками и не тенями-«карточками».
3. **Плотность без тесноты.** Base 13px, компактные контролы (24–39px), но щедрые внешние отступы.
4. **Мгновенный отклик.** Любое действие пользователя отражается в UI сразу (оптимистично),
   сеть догоняет. Спиннер — только там, где нечего показать.
5. **Ничего лишнего.** Нет декоративных иллюстраций, эмодзи, градиентных фонов (три
   исключения: мягкое radial-свечение на экране логина, маскот-кубик на экране
   Not found — §4.18 — и маскот в каске на заглушке раздела в разработке — §4.19).
   Третье исключение добавлено решением владельца при TAS-159: разделы админки
   рисуются все сразу, включая те, у которых ещё нет ручек, и пустой раздел должен
   выглядеть как стройка, а не как поломка. Маскот — тот же персонаж, что в §4.18,
   поэтому это одна иллюстративная семья, а не вторая.
   *Известное нарушение (TAS-142): `.projects-page` несёт второй radial-градиент —
   убрать или узаконить здесь одним решением, а не молчанием.*
6. **Клавиатура — первый класс.** Всё, что кликается, доступно с клавиатуры и имеет focus-стиль.

### Hard rules (нарушать нельзя)
- Не вводить новые цвета «на глаз» — только токены ниже; новый оттенок получать через
  `color-mix(in oklab, <token> N%, transparent)`.
- Не более **двух** фоновых уровней в одной плоскости (`--surface` + `--surface-2`).
- Текст никогда не наследует цвет «случайно»: у текстовых узлов задавать `color` явно
  (`var(--fg)` / `--fg-2` / `--fg-3`).
- Entrance-анимации **не должны скрывать контент**: `fill-mode` и 0%-кадр обязаны оставлять
  элемент читаемым (см. §7).
- Группы (кнопки, чипы, аватары, тулбары) верстать `flex`/`grid` + `gap`, не margin'ами и не
  пробелами в разметке.
- Минимальная кликабельная область — 28×28 (в плотных тулбарах), целевая — 32×32.

## 2. Foundations

### 2.1 Color tokens

Тема задаётся набором переменных на корневом элементе приложения. `dark` — переопределение.

```css
:root, [data-theme="light"] {
  --bg:            #f6f6f8;
  --surface:       #ffffff;
  --surface-2:     #f0f0f3;
  --surface-3:     #e9e9ee;
  --border:        rgba(22,22,32,.09);
  --border-strong: rgba(22,22,32,.15);
  --fg:            #17171b;
  --fg-2:          #56565f;
  --fg-3:          #9090a0;
  --accent:        #4f46e5;
  --accent-fg:     #ffffff;
  --shadow:        0 1px 2px rgba(20,20,40,.05), 0 4px 14px rgba(20,20,40,.05);
  --shadow-hover:  0 2px 10px rgba(20,20,40,.07);
  --shadow-pop:    0 12px 40px rgba(10,10,30,.18);
  --shadow-modal:  0 24px 70px rgba(10,10,30,.30);
  --shadow-panel:  -12px 0 40px rgba(10,10,30,.16);
  --scrim:         rgba(12,12,22,.32);
}

[data-theme="dark"] {
  --bg:            #08080b;
  --surface:       #141418;
  --surface-2:     #0f0f13;
  --surface-3:     #1c1c22;
  --border:        rgba(255,255,255,.08);
  --border-strong: rgba(255,255,255,.15);
  --fg:            #ededf1;
  --fg-2:          #9c9ca6;
  --fg-3:          #62626d;
  --accent:        color-mix(in oklab, #4f46e5, white 22%);
  --accent-fg:     #ffffff;
  --shadow:        0 1px 2px rgba(0,0,0,.5), 0 6px 18px rgba(0,0,0,.4);
  --shadow-hover:  0 2px 12px rgba(0,0,0,.5);
  --shadow-pop:    0 12px 40px rgba(0,0,0,.55);
  --shadow-modal:  0 24px 70px rgba(0,0,0,.65);
  --shadow-panel:  -12px 0 40px rgba(0,0,0,.6);
  --scrim:         rgba(4,4,8,.55);

```

**Роли:**
| Токен | Где применять |
| --- | --- |
| `--bg` | фон рабочей области (полотно доски, страница) |
| `--surface` | карточки, панели, топбар, поповеры, модалки |
| `--surface-2` | «утопленные» плоскости: колонки доски, контейнеры сегментов, поля ввода в покое, футер модалки |
| `--surface-3` | резерв (наведение на утопленные плоскости) |
| `--border` | разделители и рамки в покое |
| `--border-strong` | рамки инпутов/кнопок, hover-рамка карточки, незалитые priority-бары |
| `--fg` | заголовки и основной текст |
| `--fg-2` | вторичный текст, лейблы, иконки в покое |
| `--fg-3` | подписи, мета, плейсхолдеры, «выключенное» |
| `--accent` | primary-кнопка, активный фильтр, статус In Progress, фокус |

**Акцент — сменный.** Поддерживаемые альтернативы (менять только `--accent`):
`#4f46e5` (default) · `#2563eb` · `#0d9488` · `#7c3aed` · `#ea580c`.

### 2.2 Semantic colors

Не тема-зависимые, работают на обоих фонах.

```css
--type-task:  #4f7cf0;
--type-story: #3fa863;
--type-bug:   #e5544b;

--prio-low:    #9aa0aa;
--prio-medium: #e3a008;
--prio-high:   #e5544b;

--status-todo:        #9aa0aa;
--status-in-progress: var(--accent);
--status-done:        #3fa863;

--danger: #e5544b;
```

**Project key colors** (бейдж проекта, TAS-171): детерминированно по `projectKey`
из набора `labelColor` (§9). Вход — ключ, а не имя и не id: контракт не даёт
способа сменить ключ, и он входит в каждый `issueKey`, поэтому цвет проекта не
поедет от переименования. Цвет здесь живёт **только в тинте**: текст ключа —
`--fg-2`, см. §4.5.

**Avatar palette** (детерминированно по `userId`, TAS-171; набор восстановлен в
TAS-175): `#6366f1` `#0ea5e9` `#10b981` `#f59e0b` `#ec4899` — исходные пять
значений §2.2. TAS-171 затемнял их в oklab, потому что §4.4 печатала на заливке
фиксированные **белые** инициалы, а белый на этом наборе даёт 2.15–4.47:1. Дефект
был в фиксированном глифе, а не в заливках, и TAS-175 чинит его с той стороны:
цвет глифа вычисляется из заливки (§4.4). Замерено на восстановленном наборе:
`#6366f1` 4.47 (белый глиф), `#0ea5e9` 6.45, `#10b981` 7.05, `#f59e0b` 8.32,
`#ec4899` 5.07 — против 5.07–5.38:1 у затемнённого набора это лучше на четырёх
значениях из пяти, а на пятом выбирается тот же белый. Заливка непрозрачна, тема
на эти числа не влияет. Сама заливка против `--surface`: 4.47 / 2.77 / 2.54 /
2.15 / 3.53 в светлой и 4.11 / 6.63 / 7.24 / 8.55 / 5.21 в тёмной — в светлой
граница диска мягче, чем была у затемнённого набора (5.07–5.38), и это принято:
диск не текст и не единственный носитель смысла (§7).

**Глиф аватара — два тема-независимых значения:** `#ffffff` и `#17171b`. Второе
побайтово равно `--fg` светлой темы, но это **не** `var(--fg)` и не должно им
становиться: заливка аватара непрозрачна и от темы не зависит, а `--fg` в тёмной
теме — `#ededf1`, так что привязанный к токену глиф стал бы почти белым на янтаре
при первом же переключении темы — ровно тот отказ, который эта пара закрывает.
Тема-независимого тёмного токена в §2.1 нет, и заводить его не надо: §2.2 и есть
раздел не тема-зависимых значений, а CSS-переменная здесь была бы недоступна коду,
который делает выбор — он происходит по яркости заливки в `src/lib/format.ts`, а
не в каскаде. Оба значения живут там же, где набор, как требует §8.

Пол выбора — **4.23:1**, проверено перебором всех 16 777 216 цветов sRGB (худший
`#e101c0`, 4.2279 — это точка, где обе кандидатуры равны). Ниже 4.5:1 попадает
6.4% куба, ниже 4.0:1 — ни одного цвета. В эту полосу попадает и одно из пяти
отгружаемых значений, `#6366f1` (4.47), поэтому «весь набор проходит 4.5:1»
писать нельзя: порог, который держится всегда, — 3:1 из §7. Чёрный `#000000`
поднял бы пол до 4.58 и снял бы полосу целиком; он сознательно не выбран — это
цвет вне §2, а выигрыш составляет 0.35 пункта на цвете, которого в продукте нет.
Пересматривать это при TAS-148 не нужно: гарантия уже покрывает любой цвет,
который выберет админ.

**Дизейбл — исключение, и оно системное, а не про аватар.** Под `opacity` чипа
исполнителя (§4.1, §5.7) композит опускает пару до 2.08–2.82:1 в светлой и
2.44–3.56:1 в тёмной. То же самое `opacity` делает с любой парой — затемнённый
набор TAS-171 давал там 2.39–2.50 / 3.39–3.48, — поэтому чинится это не палитрой,
а рецептом дизейбла, если когда-нибудь будет чиниться.

**Совпадения с другими наборами возвращаются вместе с оттенками.** `#0ea5e9`,
`#ec4899` и `#6366f1` побайтово равны трём значениям `labelColor` (§9), а
`#f59e0b` и `#10b981` почти равны `--prio-medium` (`#e3a008`) и `--type-story`
(`#3fa863`); на доске это видно на одной карточке сразу. Принято, а не упущено:
какие оттенки носит продукт — решение владельца, и оно отдельно от вопроса о
читаемости инициалов на них. §7 при этом не нарушен, потому что цвет здесь нигде
не единственный носитель смысла: у метки рядом стоит её имя, у приоритета — число
баров и `title`, у аватара — инициалы и полное имя. **Разводить набор формой,
размером или кольцом не надо:** аватар — единственный круг с буквами внутри
(bug-чип §4.6 — круг 14×14 без текста, status-dot — 8px), форма уже различает, а
второй различитель был бы шумом внутри одного вьюпорта (§1).

Вход — id, а не инициалы: имя меняется, цвет человека — нет.

Цвет здесь — грубая подсказка «это разные люди», а не идентификатор. Пять
значений и хэш означают, что двое могут совпасть, и это birthday bound, а не
дефект хэша: в стеке из четырёх повтор случается примерно в 81% случаев, восемь
значений дают 59%, двенадцать — 42%. Расширять набор поэтому бессмысленно:
личность несут инициалы (ради этого они и обязаны быть читаемыми) и полное имя
в `title`/`aria-label` (§4.4).

> Оба вычисляются на клиенте, потому что контракт их не отдаёт: `color` есть
> только у метки. Цвет, пришедший с сервера, выигрывает у вычисленного —
> вычисленный это значение по умолчанию, а не запрет на выбор (выбор цвета
> проекта — TAS-148).

> Тонированный фон из семантического цвета получаем как
> `color-mix(in oklab, <color> 14%, transparent)` (для бейджей — `16%`).
> Текст — сам `<color>` у label chip и status pill. Бейдж ключа проекта —
> единственное исключение: там цвет был бы самим глифом, поэтому текст
> держится на `--fg-2` (§4.5, §9).

### 2.3 Typography

```css
--font-ui:   'Hanken Grotesk', system-ui, -apple-system, sans-serif;
--font-mono: 'IBM Plex Mono', ui-monospace, monospace;
```
Веса UI: 400 / 450 / 500 / 550 / 600 / 650 / 700. Mono: 400 / 500.

> `ui-monospace` в этом стеке — не рабочий фолбэк, а декларация намерения: его
> поддерживает только Safari 13.1+, в Chrome и Firefox он не реализован нигде и
> резолвится как несуществующее имя. Реально при отказе вебшрифта срабатывает
> generic `monospace` — то есть системный фиксированный шрифт пользователя
> (Consolas в Chrome/Edge на Windows, Menlo на macOS). Это и есть желаемое
> поведение, поэтому расширять стек в CSS не нужно; единственный ощутимый
> проигрыш — Firefox на Windows, где generic `monospace` даёт Courier New.
> Если стек всё же понадобится расширить — сначала сюда, потом в CSS, и ровно
> на одну запись (`… ui-monospace, Consolas, monospace`). Измерено в браузере
> 2026-08-12: `ui-monospace` и заведомо несуществующее имя дают идентичную
> ширину строки.
Базово: `font-size:13px; line-height:1.45; letter-spacing:-0.005em`.

### 2.6 Elevation

Только 4 уровня: `--shadow` (карточки, топбар) → `--shadow-hover` (hover карточки) →
`--shadow-pop` (поповер) → `--shadow-modal` (модалка). Больше уровней не вводить.

токен `--shadow-panel` (`-12px 0 40px rgba(10,10,30,.16)`, dark `rgba(0,0,0,.6)`).
Это не пятый уровень, а другая ось; в общую шкалу он не встраивается.

## 3. Motion

```css
--ease: cubic-bezier(.2,.7,.3,1);
--dur-hover: 120ms;   /* border-color, box-shadow, opacity, transform на hover */
--dur-enter: 160ms;   /* поповеры, модалки */
--dur-panel: 220ms;   /* slide-over */
```

```css
@keyframes tk-fade { from { opacity:.35 }              to { opacity:1 } }
@keyframes tk-slide{ from { transform:translateX(22px) } to { transform:translateX(0) } }
@keyframes tk-pop  { from { transform:translateY(7px); opacity:.55 } to { transform:translateY(0); opacity:1 } }
```

Правила:
- 0%-кадр **никогда** не `opacity:0` и не `display:none` — иначе контент пропадает при
  паузе анимации (offscreen-рендер, скриншот-тесты, `prefers-reduced-motion`).
- Hover-переходы: `transition: border-color .12s ease, box-shadow .12s ease, transform .12s ease`.
- Уважать `@media (prefers-reduced-motion: reduce)`. Реализовано через сами токены: в
  медиа-запросе `--dur-*` схлопываются в `1ms`, поэтому не нужен ни `!important`, ни
  борьба со специфичностью (см. §1, hard rules). Анимации с литеральной длительностью
  (`.auth-card-wrap`, `.skeleton-card`, `.avatar-loading`, `.value-skeleton`)
  перечислены там же поимённо — при добавлении новой литеральной анимации её надо
  добавить в этот список.
- Никаких bounce/spring и анимаций дольше 250ms. **Единственное исключение** —
  вход карточки логина `.auth-card-wrap` (`tk-pop` 500ms из прототипа): экран
  показывается один раз за сессию и ни с чем не конкурирует. Исключений внутри
  рабочих экранов не бывает.

## 4. Components

Спека: назначение → анатомия → размеры/токены → состояния.

### 4.1 Button
- **Primary:** `background:var(--accent); color:var(--accent-fg)`, height 32–34 (форма 39),
  radius 9, padding 0 13–16, 12.5–13.5px/600. С иконкой — `gap:6`, иконка 13.
  hover: `filter:brightness(1.06)`; active: `brightness(.96)`.
- **Secondary / outline:** `border:1px solid var(--border-strong)`, фон прозрачный,

### 4.4 Avatar
Круг, `background: <avatar color>`, `color: <глиф, вычисленный из заливки>`,
инициалы (2 символа, uppercase), `font-size: ~40% диаметра`, weight 600.
Размеры — см. §2.7.
- **Глиф считается из заливки, а не задаётся** (TAS-175): берётся относительная
  яркость заливки по WCAG 2.x, возвращается то из двух значений §2.2
  (`#ffffff` / `#17171b`), которое даёт больший коэффициент. Не таблица по
  набору: заливка — это любой hex, прошедший контрактный
  `^#[0-9A-Fa-f]{6}$`, а с TAS-148 её выбирает админ, так что таблица покрыла бы
  ровно те пять значений, у которых и без неё всё в порядке. Пол вычисления и
  его проверка — в §2.2.
- **Заливка и глиф ставятся вместе или никак.** Обе части задаёт компонент одним
  инлайновым `style`; половина пары — заливка поверх стилевого `color` — и есть
  нечитаемый случай. Правил, задающих `color` на `.avatar` по месту, в CSS быть
  не должно: `.avatar-stack .avatar { color:#fff }` снято в TAS-175, оно
  перебивало ещё и `--fg-3` у `.avatar-empty`. Единственный оставшийся `color` на
  `.avatar` — фолбэк в паре с `background: var(--accent)`, и берёт он
  `var(--accent-fg)`, а не литеральный `#fff`: это пара, а не общий цвет глифа.
- **Unassigned:** прозрачный фон, `border:1.5px dashed var(--border-strong)`, без текста.
- **Stack:** `margin-right:-7px`, `border:2px solid var(--surface)`, показывать до 4,
  далее «+N». Перекрытие срезает правый край глифа у всех, кроме самого узкого:
  при диаметре 24 и 10px/650 видимая ширина 17px вмещает строку не шире 10px, а
  реальные пары — 9.2–13.5px (замерено: `AI` 9.2 — влезает, `SR` 11.7 — срез
  0.9px, `PN` 12.4 — 1.2px, `ML` 13.5 — 1.8px). До TAS-175 срез прятался в
  светлой теме, потому что белый глиф уходил в белое кольцо; тёмный глиф режется
  видимо. Принято, потому что личность несут не последние 13% буквы: полное имя
  всегда в `title`/`aria-label`, и стек — единственное место, где имени нет
  рядом. Если когда-нибудь чинить — уменьшать перекрытие до `-4px` (видимые 20px
  вмещают до 16px), а не увеличивать диаметр.
- **Selectable** (фильтр по исполнителю): активный — `outline:2px solid var(--accent);
  outline-offset:1.5px`; неактивные — `opacity:.85`.
- Всегда `title` / `aria-label` с полным именем.

### 4.5 Badge / Pill
- **Project key:** mono 11px/500, padding 4 8, radius 7, letter-spacing .02em,
  фон `color-mix(in oklab, <projectColor> 16%, transparent)`, текст `--fg-2`
  (5.13–6.40:1 в обеих темах на всех восьми значениях набора, TAS-171).
  Текст здесь — **не** `<projectColor>`, в отличие от label chip ниже, и различие
  принципиальное: у метки цвет стоит рядом со смыслом, а у ключа он был бы самим
  глифом. Порог 3:1 из §2.3 для моно-ключей на этом рецепте берут два значения
  набора из восьми (§9), поэтому цвет уходит в тинт, а ключ читается.
  Тинт не поднимать в компенсацию: на 24% минимум в тёмной падает до 4.34.
- **Count pill** (в заголовке колонки): 11px/600 `--fg-3`, `background:var(--surface-2)`,
  padding 1 7, radius 20.
- **Status pill** (в панели): height 28, padding 0 12, radius 8, 12.5px/600,
  фон `color-mix(in oklab, <statusColor> 14%, transparent)`, текст `<statusColor>`.
- **Label chip** (метка задачи, TAS-169): height 20, padding 0 8, radius 20,
  11.5px/600, фон `color-mix(in oklab, <labelColor> 16%, transparent)`,

  задаётся инлайном; значение, не проходящее контрактный `^#[0-9A-Fa-f]{6}$`,
  заменяется на `--accent`, а не рисуется как есть. Имя метки — всегда текст:
  цвет здесь не единственный носитель смысла ровно по причине из §4.6.
  Съёмная метка несёт внутри кнопку 15×15 на `currentColor` с обязательным
  `aria-label` «Remove <name>»; длинное имя обрезается многоточием, чтобы чип
  не растягивал строку.

### 4.13 Top bar / Filter bar
Есть два бара, и они разные. **Бар доски** — height 52, `background:var(--surface)`,
нижний бордер, `padding:0 18`, `gap:12`. Порядок: назад → project key → название →
контекст («Board») → **spacer** → поиск по проекту → уведомления → тема → primary «New»
→ аватар. **Общий бар** (`/projects`, `/admin`) — тот же 52 и `padding:0 22`, и несёт
логотип → глобальный поиск (§5.4, ищет по всем доступным проектам) → уведомления →
тема → аватар.

**Колокольчик стоит в обоих барах, и это не дублирование** (TAS-185). Бары
взаимоисключающие: доска рисует свою шапку и общий бар не использует, так что на
любом экране колокольчик ровно один. Первая редакция этого абзаца утверждала
обратное — «уведомлений на нём нет: они про задачи проекта», — и утверждение было
ложным в момент написания: контракт называет ручку inbox уведомлений **текущего
пользователя**, проекта в запросе нет вовсе. Следствие ошибки было видно на самом
частом типе: «вам назначена задача» приходит обычно про проект, который сейчас не
открыт, а увидеть его можно было, только зайдя на доску какого-нибудь другого.
Контракт выше этого документа по авторитету — обоснование заменено, а не снято, чтобы
следующий читатель не вывел ту же ошибку заново.

**Ниже 400 логотип общего бара — только знак, без слова** (TAS-185). Не украшение:
колокольчик забрал 44 пикселя у единственного, что в этом баре умеет сжиматься, и на
320 поле ввода становилось **4 пикселя** — запрос печатается, результаты внизу
находятся, а на экране не видно ни буквы. Порог схлопывания уехал с ~276 вьюпорта на
~320, то есть внутрь полосы, по которой этот документ меряет (§1). Знак при этом
сохраняет и ссылку, и область нажатия, которых §4.13 требует от верха страницы, —
поэтому это записанный вариант компонента, а не отступление от §4.14: та задаёт размер
поля **в покое**, а поведение на узких живёт в §4.20.

Три детали рецепта, каждая замерена, и каждая перестаёт работать без остальных:
`min-width:44` на ссылке логотипа обязателен — без него область нажатия падает до 33×44,
и один разрыв §7 меняется на другой. Граница ровно **400**: обрезка начинается ниже
395.3, а 412 и 414 не обрезаются, и снимать там слово незачем. `gap` в баре и в хвостовой
группе идёт на **8** (§2.4 держит 5–8 для inline-групп) — без этого на 320 остаётся 34
пикселя ввода, то есть **хуже, чем было до колокольчика**. С ним: 54 на 320, 109 на 375,
124 на 390.

Побочное следствие, которое легко проглядеть: `gap:8` двигает **сам колокольчик** на 8
вправо, потому что он первый в группе, а группа прижата правым краем. Панель за ним —
270 на 390, 255 на 375, 200 на 320, а порог `--pop-floor` уехал с 314 на 306. Все
отношения целы: правый край панели равен правому краю колокольчика, левый ложится ровно
на `--bar-gutter`.

**Хвост бара — одна неразрывная группа, прижатая вправо** (`margin-left:auto`), и
аватар в ней всегда последний. Это не вкусовщина. Ниже 820 бар доски переносится, а
перенесённая строка флексбокса пакуется по `flex-start`: свободными соседями «New» и
аватар оказывались посреди второй строки, и поповер, привязанный `right:0` к аватару,
разворачивался влево от того места, где аватар остановился, и уходил за левый край
экрана. Группа держит их вместе, `margin-left:auto` держит группу справа, и аватар
оказывается там, где его и ищут (TAS-179).

Ширина любого поповера в баре ограничена вьюпортом, с настоящими значениями, а не
формулой: меню профиля `min(276, 100vw - 24)`, панель поиска `min(420, 100vw - 44)` —
поле в клампе равно удвоенному `padding` своего бара (§2.4), поэтому панель заходит
внутрь обоих краёв, а не одного.

**«Своего бара» — это теперь переменная, а не подразумеваемое число** (TAS-185).
Пока колокольчик жил только на доске, кламп нёс литеральные 12 с комментарием «боковой
отступ бара доски». У общего бара отступ 22, и кламп на нём срабатывает — панель
начиналась бы в 12 от края экрана, то есть на десять пикселей внутрь от собственной
кромки бара, вровень ни с чем. Отступ объявляется как `--bar-gutter` по одному на бар
(22 у общего, 18 у бара доски, 12 в блоке ≤820) и читается и паддингом, который его
задаёт, и клампом, который ему отвечает. Два числа, которые обязаны сходиться, — в
третий раз в этом файле, и в первый раз названные до того, как разошлись.

**Поповер всегда висит на своём триггере, и ограничение — это ширина, а не привязка**
(TAS-181). Ниже 820 бар доски переносится, и первая попытка развести поповер с краем
экрана переносила привязку с триггера на сам бар. Край она чинила и ломала другое:
`top` считается от бара, бар на 390 высотой 141, и панель уведомлений падала под всю
шапку — визуально под строкой поиска, а не под колокольчиком, которому принадлежит.
Правильный размен обратный: привязку сохранить, а ширину сузить. У поповера
уведомлений третий член клампа —
`min(312, 100vw - 24, «правый край колокольчика» - 12)`, и снизу он ограничен **186**.
Замеренная граница — 185: на ней заголовок ещё держит одну строку, на 184
«Mark all read» переносится, а это ломается уже не строка списка, а сама панель.
Пол взят на пиксель выше границы намеренно — значение, стоящее ровно на обрыве,
переходит его от любого будущего изменения кегля или отступа.
До 506 по ширине это 312, на 390 — 196.5; за полом панель не сужается дальше, а
съезжает. Его правый край совпадает с правым краем колокольчика везде, где пол не
связывает.
Позицию триггера публикует JS в `--trigger-right` / `--trigger-bottom`, потому что
CSS её выразить нечем: колокольчик — **первый** в прижатой вправо группе, и никакой
процент от предка про него не скажет. По той же причине вертикальный кламп теперь
`100vh - «низ колокольчика» - 18`, а не `100vh - 100% - 12`: прежняя формула работала
лишь пока верхом панели был низ бара.

Отсюда правило с предусловием, а не два поведения под одним абзацем: **к бару
поповер привязывается только там, где бар не может перенестись; где может — висит на
триггере и отдаёт ширину**, вплоть до той, на которой ломается его собственный
заголовок. Общий бар (`/projects`, `/admin`) зафиксирован на 52 и не переносится
никогда — замерено на 320, 360, 375, 390, 500, 600, 700 и 820, — поэтому панель
поиска привязку к нему сохраняет: от строки своего триггера её оторвать нечем. Бар
доски переносится, поэтому поповер уведомлений висит на колокольчике. Это структурное
различие баров, а не вкус.

Первая редакция этого абзаца обосновывала асимметрию иначе — «420 сузились бы
вчетверо сильнее, чем 312». Замер это опроверг: правый край поля поиска на 390 равен
284, то же правило дало бы панели 262, то есть −37.6% против −37.0% у колокольчика.
Обе сужаются одинаково, разница 42 пикселя, а не вчетверо. Аргумент был втрое больше
того, что даёт раскладка, и держался ровно до первого замера.

Спейсер общего бара при этом **остаётся живым**, и это не мелочь. Убрать его, отдав
поиску `flex: 1 1`, — значит отдать полю весь запас бара: измерено 609 на 820, 549 на
760, 389 на 600 против положенных §4.14 двухсот двадцати, то есть поле во весь хедер с
панелью, свисающей с его правого конца. С `flex: 0 1 220px` и живым спейсером поле
держит 220 вплоть до 500, а ниже сжимается — 178 на 400, 168 на 390, 153 на 375, 98 на
320 (§4.20: ниже 400 логотип теряет слово, иначе там оставалось бы 4 пикселя ввода), и
высота бара остаётся 52
на всей полосе. Прижать аватар вправо достаточно, чтобы симптом
ушёл; ограничение по вьюпорту нужно, чтобы он не вернулся, когда следующая раскладка
снова сдвинет триггер. Инвариант закреплён в `e2e/topbar-popovers.spec.ts`: панель не
пересекает ни один край экрана.
Логотип в шапке — ссылка в `/projects` на всех экранах с сессией; на `/login` он
остаётся простым знаком, потому что возвращаться там некуда. Это не замена
выходу из области (§5.8), а конвенция, с которой читатель приходит: верх
страницы обязан куда-то вести. Как интерактивный элемент он подчиняется
общему полу §1 — область не меньше 32 в высоту, на тач-ширинах 44, — и
подсвечивается фоном `--surface-3`, а не приглушением текста: все соседние
hover в шапке ведут к `--fg`, и один, ведущий от него, читается как
выключение. Именно `-3`, а не `-2`: плоскость шапки — `--surface`, и `-2`
против неё даёт 1.04:1 в тёмной теме, то есть не даёт ничего (§2.1 держит
`-3` ровно для hover по утопленной плоскости). Соседняя кнопка темы обходится
`-2` потому, что дополнительно ведёт `--fg-2` к `--fg`; у логотипа знак и так
на `--fg`, и фон — единственный оставшийся канал.
Filter bar: `min-height:46`, тот же фон/бордер, `column-gap:14`, `row-gap:11`,
`padding:6 18` (на узких — `6 12`): сегмент типов → разделитель (1×18 `--border`) →
«Assignee» + `All` + аватары → «Clear» (если активны фильтры) → «X of Y».
**46 — это пол, а не фиксированная высота.** Ровно 46 держится, пока хватает одной
строки. Устойчивая величина здесь — не ширина вьюпорта, а ширина содержимого: бару
нужно 766px под контент, со «Clear» — 847px; это не меняется, когда меняется padding.
На доске Taska Platform (4 участника, роль ADMIN) это даёт одну строку от ~791px и,
со «Clear», от ~883px. Числа плывут по данным — у MEMBER'а без кнопки управления
метками второй порог падает до ~837, — поэтому это замер, а не токен. Выше 820
нефильтрованный бар не переносится вовсе, так что единственная полоса переноса выше
брейкпоинта — фильтрованная, 821–882px. Уже — переносится по строкам, по строке на
перенос; порядок при переносе сохраняется. Переносится, а не скроллится
вбок: горизонтальная полоса уводила «X of Y» за правый край и ничем не сообщала,
что показала не всё, а §5.4 требует показывать счётчик всегда.
«X of Y» всегда прижат к правому краю **своей** строки, и держит это
`margin-left:auto` на самом счётчике, а не spacer.
«Clear» — часть левой группы: он идёт сразу за последним фильтром, который сбрасывает,
и к правому краю не прижимается. Правый край строки принадлежит только счётчику. На
переносящемся баре читается так же: «Clear» открывает последнюю строку слева,
«X of Y» закрывает её справа. Spacer делит ровно одну строку;
в переносящемся баре он снят (`display:none`), иначе он съедает остаток той строки,
на которую попал, и выбрасывает счётчик на отдельную. `flex:0` тут не годится —
нулевой элемент всё равно собирает `column-gap` с обеих сторон.
Каждый ребёнок бара — `flex:none`: все они меряются по содержимому, и без этого
узкий вьюпорт жмёт их до min-content вместо переноса (так «4 of 4» и складывалось
в три строки шириной со слово «of»). Исключение — ряд аватаров: он растёт по
данным и переносится внутри себя.

### 4.18 Not found / no access screen
Полноэкранный маршрут вне app shell (как логин): центрированная колонка,
`min-height:100vh` + `min-height:100dvh` (та же пара и по той же причине, что у shell'ов в §5.1), фон `--bg`. Показывается для неизвестного URL (`*`) и когда
загрузка проекта на борде падает с NOT_FOUND / PERMISSION_DENIED (404/403).
Текст **намеренно не различает** «страницы нет» и «нет прав» — не раскрываем
существование чужих проектов.

Третий случай — `/admin` у пользователя, который не `GLOBAL_ADMIN` (§5.1).
Сюда же попадает профиль, который не загрузился вообще: `GET /users/me` упал по
транспортной причине — это не 404 и не 403, но подтвердить админство мы не
можем, а экран даёт выход. Отклонение осознанное, зафиксировано здесь, чтобы
§4.18 продолжал описывать то, для чего экран на самом деле используется.

Пока роль неизвестна, `/admin` рисует **пустую плоскость** `--bg` — ни топбара,
ни скелетона (отклонение от §5.6). Показать шапку и через мгновение заменить её
экраном «не найдено» — та самая «секунда правдоподобного интерфейса», против
которой §4.18 и существует. Для глаза там ничего, для скринридера — визуально
скрытый `role="status"`: `aria-busy` на пустом лендмарке не сообщает ничего.

- **Маскот** — вторая разрешённая иллюстрация после свечения логина:
  расплавившийся 3D-кубик Taska с глазами-крестиками и высунутым языком.
  Сгенерирован владельцем во внешней модели (в исходном PNG первого рендера —
  подписанный C2PA-манифест: `gpt-image`, `trainedAlgorithmicMedia`).
  Ширина бокса 360 (`max-width:78vw`), сама фигура вписана в кадр 3:2 и
  оптически занимает около 260 — размер задаётся по фигуре, не по кадру.
  Декоративный: весь смысл несут заголовок и текст.
  Собственной тени не нужно: лужа с каплями в самой картинке уже сажает
  фигуру на плоскость.
- **Маскот собирается из каналов и следует за `--accent`** (TAS-159). Вместо
  одного запечённого кадра — три слоя в `src/assets`:
  `mascot-notfound-alpha.webp` (силуэт-маска), `-shade` (умножение: белый там,
  где поверхность берёт акцент как есть, темнее там, где форма отворачивается),
  `-light` (экран: чёрный везде, кроме бликов и логотипа). Формула —
  `accent × shade + light`, обрезано по alpha; собирается компонентом
  `TaskaMascot` внутри `isolation:isolate`, иначе blend-режимы достанут до
  страницы под маскотом. У каждого канала своя прозрачность, поэтому маской
  накрыт только слой заливки.
  Прежнее ограничение — «фиолетовый запечён в пиксели, смена акцента требует
  перерисовки» — этим снято: цвет теперь токен, как везде (§2.1).
  Исходники каналов — `docs/design/mascot-channels/` (PNG 1536×1024, ~2.7 МБ
  на оба маскота); без них каналы не пересобрать. Исходный рендер первой версии
  с манифестом остаётся в `docs/design/mascot-not-found-source.png` как запись
  происхождения персонажа.
- **Заголовок** «Page not found» — page title (22/700, `--fg`, -0.025em), `h1`.
- **Текст** 13/400 `--fg-2`, `max-width:340`, центр, `text-wrap:pretty`;
  покрывает оба случая одной фразой.
- **Действие** — primary «Go to projects» (§4.1): семантически ссылка на
  `/projects`, стилизованная как `.primary-button`.
- Вход — `tk-pop var(--dur-enter)` (reduced-motion схлопывает через токены §3),
  0%-кадр читаем. Маскот въезжает вместе с блоком, собственной анимации у него
  нет.
- **Загрузка проекта не ретраится на 404/403.** Глобальный `retry: 1` (react-query,
  `retryDelay` 1000мс) относится к 404 как к транзиентной ошибке, и борд успевал
  показать секунду правдоподобного чужого хрома — топбар, фильтр-бар, колонки —
  ровно перед экраном, который существует, чтобы этого не показывать.
  Project-scoped запросы борда отсеивают такие ошибки предикатом `retry`;
  замерено: 1044мс → 36мс.

### 4.19 Заглушка раздела в разработке
Экран раздела, который уже есть в навигации, но ещё не имеет ручек (§5.8).
Живёт **внутри** admin-shell: рельс, топбар и заголовок раздела на месте —
пустой здесь контент, а не страница. Этим он отличается от §4.18, который
именно что заменяет собой всё.

- **Маскот** — третья и последняя разрешённая иллюстрация (§1): тот же кубик
  Taska, что на Not found, но в строительной каске, с ограждением, мигалкой и
  чертежом. Собирается тем же `TaskaMascot` из тех же трёх каналов
  (`mascot-building-alpha|shade|light.webp`) и так же следует за `--accent`.
  Ширина бокса 256 (`max-width:70vw`), фигура оптически занимает около 220.
  Декоративный: смысл несут заголовок и текст.
- **Четвёртый слой — `mascot-building-static.webp`**, поверх собранного, без
  blend-режима: мигалка, ластик и грифель карандаша. Причина не в семантике
  цвета — это декоративная иллюстрация, её мигалка ничего в продукте не
  сигнализирует, и ссылаться здесь на «предупреждающий сигнал» значило бы дать
  будущему читателю основание завести оранжевый элемент в настоящем UI. Причина
  в идентичности предметов: янтарная мигалка, розовый ластик и деревянный
  грифель — это то, чем эти предметы являются, а акцент красит материал кубика.
  Поэтому все три лежат в одном слое, и поэтому у маскота Not found такого слоя
  нет: в нём нечему оставаться нетонированным.
- Не анимируется: мигалка на картинке уже горит, а мигающий элемент в служебном
  разделе — ровно то, чего §1 просит избегать.
- **Заголовок** 15/600 `--fg`, имя раздела в предложении: «Events — раздел в
  разработке».
- **Текст** 12.5/400 `--fg-2`, `max-width:360`, `text-wrap:pretty`: одна фраза
  о том, что раздел появится, и **ключ истории, которая его откроет** — читатель
  этого экрана единственный, кому ключ полезен, и он же обычно тот, кто может
  спросить о статусе.
- Ключ истории — ссылка на Jira, `--fg-2` → `--accent` на hover, внешняя
  (`target="_blank"`, `rel="noreferrer"`).
- Никаких кнопок. Заглушка ничего не предлагает сделать: единственное осмысленное
  действие — уйти в другой раздел, а он уже в рельсе слева.
- Вход — `tk-pop var(--dur-enter)`, 0%-кадр читаем (§7).

Компонент один на все пустые разделы; различаются только имя раздела и ключ.
Когда раздел получает ручки, заглушка снимается вместе с записью в §5.8, а не
остаётся под флагом.

- **Поле** — `.search-box` шириной 220 (§4.14), ниже 820 `flex: 0 1 220px`

  бара и разъезжается до 609 на 820, что и было дефектом TAS-179.
- **Панель** — `width: min(420, calc(100vw - 44))`, `top:38; right:0`,
  `radius:13`, `box-shadow:var(--shadow-pop)`, `tk-pop var(--dur-enter)`.
  44 — это удвоенный собственный `padding` общего бара (§2.4), и именно он
  заводит панель внутрь **обоих** краёв, а не одного. Выше ~464 кламп не
  срабатывает вовсе.
- **Список** — `max-height:340; overflow:auto`, страница 8 попаданий.
  Строка: `padding:9px 12px`, `gap:8`, разделитель `1px --border`; ниже 820
  `padding:12` и `min-height:44` — пол §7, записанный как пол.
- **Строка попадания** — тип-чип + ключ 11.5 `--fg-3` + summary 12.5 `--fg`
  (эллипсис) + полосы приоритета справа. Ассигни нет: вне проекта нет
  списка участников, а голый UUID — не факт, который стоит печатать.
- **Активная строка** — `background:var(--surface-3)` **и**
  `box-shadow: inset 0 0 0 2px var(--accent)`. Кольцо здесь не украшение:
  `aria-activedescendant` не двигает фокус, поэтому заливка — единственный
  индикатор выделения, а одной заливки не хватает ни в одной теме.
  Измерено: `--surface-2` даёт 1.04 в тёмной и 1.14 в светлой, `--surface-3`
  — 1.08 и 1.21, то есть оба не дают ничего; кольцо даёт **4.39 тёмная /
  5.20 светлая** к своей заливке и проходит порог 3:1 (§7). Акцент тот же,
  что у фокус-ринга поля, так что акцент на экране остаётся один (§1).
- **Строка на углу панели берёт её внутреннюю дугу, а не прямой угол** (TAS-181).
  Панель скруглена на 13 и обрезает `overflow:hidden`; строка — прямоугольный `li`
  с inset-обводкой, поэтому у первой и последней строки скруглённый угол панели
  срезал прямой угол обводки, и штрих обрывался. Виднее всего на единственном
  результате, где строка сразу и первая, и последняя. Лечится согласием радиусов:
  `--pop-radius` объявлен на панели, строка на углу берёт `calc(--pop-radius - 1px)`
  — минус бордер панели, — и обе описывают одну дугу, так что обрезать нечего.
  Это снова два числа, которые обязаны сходиться, и именно поэтому радиус назван, а
  не вписан дважды. Радиус вешать на строку, стоящую на углу **панели**, а не
  списка: над списком может стоять `ApiNotice`, а под ним всегда подвал.
- **`scroll-padding-top: var(--pop-radius)` на списке** — то, до чего радиус не
  дотягивается. В полосе ниже 460 (см. ниже) список короче страницы, и
  `scrollIntoView` ставит строку вплотную к краю скролл-порта, то есть в ту же
  дугу, но уже не на `:first-child`. Замерено без него на 667×375: строка садится в
  3.0px от верха списка с нулевым радиусом внутри 12px дуги; с ним — в 13.
- **Текст на активной строке берёт `--fg-2`, а не `--fg-3`.** Смена заливки
  двигает всё, что на ней лежит: на `--surface-3` ключ в `--fg-3` измеряется
  как 2.82 в тёмной и 2.60 в светлой, то есть тёмная перешла порог §7 именно
  из-за подсветки, а выбранная строка несла самый тусклый идентификатор на
  панели — обратное тому, что выделение должно делать. С `--fg-2` это **6.23
  тёмная / 6.00 светлая**. Правило шире этой строки: меняя токен поверхности,
  перемерить текст на ней.
- **Что этот выбор стоил и почему принят.** Подсветка отнимает у тип-чипа
  примерно 0.4 в тёмной и 0.5–0.7 в светлой — измерено по каждому чипу против
  **обеих** плоскостей, а не по разным чипам против разных:

  | чип | тёмная, `--surface` → `--surface-3` | светлая |
  | --- | --- | --- |
  | Story | 6.12 → 5.65 | 3.00 → **2.48** |
  | Task | 4.79 → 4.42 | 3.84 → 3.17 |
  | Bug | 4.99 → 4.60 | 3.68 → 3.04 |

  В тёмной все три остаются с запасом над 3:1. В светлой Story уходит под
  порог — и это записано в §7, а не спрятано здесь. Чип всё равно не
  перекрашивается: тип несёт себя не цветом одним (§2.2 — цвет плюс форма плюс
  скрытый текст строки), а Story и до этой истории стоял ровно на 3.00, так что
  под порог его увела бы любая заливка вообще. Полосы приоритета не трогаются:
  незаполненная полоса обязана читаться как отсутствующая.

  Первая редакция этого абзаца утверждала падение с 6.12 до 4.42 как судьбу
  одного чипа. Это были Story на `--surface` и Task на `--surface-3` — два
  разных чипа, и цена выходила вчетверо больше настоящей, в пользу решения,
  которое абзац защищает. Правило, которое из этого следует и стоит дороже
  самой цифры: мерить один и тот же элемент против обеих плоскостей, а не два
  элемента против одной каждый.
- **Высота списка считается от страницы, а не назначается.** `max-height:340`
  на десктопе — восемь строк по 37.1 это 296.8, кап не срабатывает. Ниже 820
  строка равна 44 (пол §7), и восемь строк это ровно **352**: кап там 352, а
  не 340, иначе последняя строка обрезается на 12px. Обрезается именно та, на
  которую первым же `ArrowUp` заворачивает выделение. Два числа, которые
  обязаны сходиться: меняя высоту строки или размер страницы, пересчитать кап. Пинится `e2e/topbar-popovers.spec.ts`, потому что измерение
  в документе не падает, когда кто-то двигает одно из них.
- **По вертикали зажимается панель, а не список.** §4.13 зажимает ширину
  каждого поповера бара по вьюпорту; вертикальной половины этого правила
  долго не было, и на 820×420 панель уходила за нижний край на 28.7 при
  `body{overflow:hidden}` — то есть последняя строка и подвал становились
  недостижимы вовсе. Кап ставится на `.global-search-pop`
  (`max-height: calc(100vh - 66px)`, флекс-колонка, список `min-height:0`,
  подвал `flex:none`), а не на список: над строками может стоять `ApiNotice`
  высотой 69.5 с полями, которой кап на списке не видит, и с ней подвал всё
  равно оставался на 61 под сгибом. Отдаёт высоту и прокручивается список;
  подвал — единственная строка, до которой нельзя доскроллить, — не отдаёт.
  66 это 55 (осевший верх панели: 51 у бокса бара плюс отступ 4) плюс 11
  просвета. На высоких вьюпортах кап не срабатывает: 820×900 и 390×844 дают
  те же 352 и ту же панель.
- **Ниже 460 по высоте список короче своей страницы, и это надо знать по
  имени.** Замерено попиксельно на ширине 820: **460** — самая низкая высота, на
  которой восемь строк ещё помещаются; ниже список теряет по пикселю на пиксель
  по правилу `min(352, 100vh − 107.7)` (107.7 = 66 клампа + 2 своих бордера +
  39.7 подвала). Полоса «ширина ≤ 820 **и** высота < 460» — единственная, где
  кап панели перебивает кап от страницы, и телефон в альбомной (667×375) лежит
  внутри неё.
- **Поэтому активную строку подкручивает JS, а не CSS.** Пока список равен
  своей странице, подкручивать нечего; в полосе выше — есть, а `scrollTop`
  контейнера из CSS в ответ на `aria-activedescendant` не двигается никак. Это
  паттерн APG: `scrollIntoView({block:"nearest"})` по смене активного индекса,
  без `behavior` (мгновенно — деградировать под `prefers-reduced-motion`
  нечему) и без движения фокуса. На 667×375 без него у выбранной строки было
  **ноль** пикселей на экране при живом `aria-activedescendant` и работающем
  `Enter`. `nearest` —но-оп там, где строка и так видна: на 1440×900 и 390×844
  `scrollTop` остаётся 0.
  - Соседние поверхности этого не требуют, и по одной причине: строки поповера
    уведомлений — настоящие `<button>`, а карточки группы на доске —
    настоящие `<a>`, и туда браузер скроллит сам. Комбобокс держит фокус в
    поле, поэтому он единственный, кому нужен явный скролл.
  - Эффект индексирует `children` позиционно, и это верно ровно пока
    содержимое `<ul>` — только строки результатов. Заголовок или разделитель
    внутри списка уведёт скролл не на ту строку, а не сломается заметно.
- **Четыре ответа, и они разные**: «короче трёх символов», «ищем», «ничего
  не нашлось» и список. Первые три — `--fg-2`, потому что в этих состояниях
  текст и есть всё содержимое панели, а не мета рядом с ним. Отказ чтения —
  `ApiNotice` со словами гейтвея и `X-Request-Id`, и он никогда не
  сворачивается в «ничего не нашлось» (§5.6).
- **Клавиатура** — стрелки с заворотом, `Enter` открывает, `Esc` закрывает
  и вторым нажатием чистит поле, `Tab` закрывает и уходит дальше, клик вне
  закрывает. Один общий хук на все поповеры бара (§4.12, §4.16).
- Попадание, чей проект не разрешился по префиксу ключа, не ссылка:
  `aria-disabled`, с одной строкой о причине.

## 5. Patterns

### 5.1 App shell и маршруты
Фиксированный топбар (+ фильтр-бар на доске) → прокручиваемая область контента.
`height:100vh` + `height:100dvh` (фолбэк первым); `display:flex; flex-direction:column;
overflow:hidden`; скроллит только контент.
`vh` на iOS (Safari и Chrome) — это *large viewport*: высота, которую страница имела бы
с убранными панелями браузера, а они не убраны, пока читатель не потянет страницу.
Shell, который режет собственный overflow и отдаёт скролл одной области внутри себя,
обязан меряться по видимой высоте — иначе низ этой области стоит под нижней панелью
браузера и до него нельзя доскроллить. Не `svh`: он оставил бы мёртвую полосу под
shell'ом на всё время, пока панели убраны.
Исключение — экран логина: он не отдаёт скролл внутренней области, поэтому скроллит
сам (`overflow:auto`) и центрируется через `align-items:safe center`. Без `overflow`
низкий вьюпорт режет карточку без выхода, и `dvh` делает это раньше `vh`, заодно
убирая тот самый протяг страницы, которым читатель выбирался; без `safe` возвращается
только нижняя половина обрезки — обычный `center` делит переполнение поровну, а
прокрутить контейнер выше `scrollTop: 0` нельзя, так что верх карточки остаётся
недостижимым (замерено на 740×300: верх обёртки на −58px, до логотипа нет пути ни
указателем, ни с клавиатуры).

**Про пару `vh` + `dvh` — честно, потому что в собранном артефакте её нет.**
Lightning CSS (CSS-трансформер Vite; в проекте нет ни `browserslist`, ни
`build.cssTarget`) выбрасывает первое из двух объявлений: его дефолтный таргет уже
знает `dvh`. В `dist` остаётся только `100dvh`, на дев-сервере живут оба. Пара
остаётся в исходнике как зафиксированное намерение, и потери здесь нет: этот
стилевой файл повсюду опирается на `color-mix(in oklab, …)`, а его база (Chrome 111 /
Safari 16.2) *новее* базы `dvh` (Chrome 108 / Safari 15.4) — браузер, который вообще
способен отрисовать цвета Taska, про `dvh` уже знает. Стоит сказать это прямо, а не
оставлять комментарий, обещающий страховку: без `dvh` `height` схлопнулся бы не в
`100vh`, а в `auto`, то есть `overflow:hidden` поверх колонки авто-высоты — деградация
хуже той, которую «фолбэк» будто бы обещает. CI проверяет, что `100dvh` дожил до
`dist`: если тулчейн однажды выбросит не ту строку, это должно падать, а не исчезать
молча.

| Экран | Route | Доступ |
| --- | --- | --- |
| Login / Accept invite | `/login`, `/invite?token=…` | публичный |
| Projects | `/projects` | по сессии |
| Board | `/projects/:projectId/board` | по сессии |
| Issue card | `/projects/:projectId/issues/:issueId` | по сессии |
| Admin | `/admin/*` (§5.8) | по сессии **и** `globalRole = GLOBAL_ADMIN`; иначе §4.18 |
| Not found / no access | `*` (fallback); также борд при NOT_FOUND / PERMISSION_DENIED (§4.18) | публичный |
| Notifications | поповер, без маршрута | — |

Issue card — **slide-over поверх доски**, а не отдельная страница: URL меняется,
доска остаётся под затемнением, закрытие панели возвращает на `…/board`.
Ручки для каждого экрана — в контракте `docs/contract/openapi.yml`.

**Приватные маршруты.** `/projects`, `…/board`, `…/issues/:issueId` и `/admin`
открываются только с сессией: гвард спрашивает у `TaskaApi` синхронное «есть ли
у клиента учётные данные» и без них отдаёт `/login`, запомнив запрошенный адрес —
после входа пользователь возвращается именно туда, а не в общий список проектов.
У `/admin` поверх сессии есть вторая проверка — `globalRole = GLOBAL_ADMIN`, и
она уже не про гвард, а про то, что рисует сам экран (§4.18).
Голый заход на `/` — это редирект в `/projects`, поэтому до гварда он доходит
уже как эта страница и после входа возвращается в неё же; отдельного случая ему
не нужно. Ни в одном из этих случаев форма ничего дополнительно не объясняет:
форма входа после клика по закрытой ссылке объясняет себя сама. Зеркальное
правило: посетителя, у которого сессия уже есть, `/login` отправляет в
`/projects`. `/invite` остаётся публичным намеренно — инвайт принимают и будучи
залогиненным под другим аккаунтом; `*` (Page not found) тоже вне гварда:
несуществующий адрес должен отвечать «страницы нет», а не формой входа, которая
намекала бы, что страница существует и просто закрыта (§4.18). Наличие сессии —
не право доступа: сервер остаётся авторитетом (§5.7).

**Смерть сессии.** 401, который не удалось починить refresh-ом, обрабатывается в
одном месте, а не каждым экраном по-своему: `App` подписан на сигнал от
`TaskaApi`, чистит кэш react-query (ответы принадлежали сессии, которой больше
нет) и возвращает пользователя на `/login` с запомненным адресом страницы, где
это случилось, и с объяснением «Your session expired. Sign in to continue.».
Так как переход происходит без просьбы пользователя, фокус переводится на само
объяснение (§7) — иначе о нём не узнает ни скринридер, ни клавиатура. Осознанный
выход из аккаунта объяснения не показывает: это не истечение сессии.

### 5.2 Board layout
Полотно `flex; gap:14; overflow-x:auto; align-items:flex-start`, колонки во всю высоту,
внутренний скролл — у списка карточек, не у полотна.

### 5.3 Drag & drop
- Источник — карточка задачи; цель — колонка (в MVP порядок внутри колонки не сохраняем).
- `dragstart` → запомнить `issueId`, `effectAllowed='move'`; `dragover` на колонке →
  `preventDefault()` + подсветка; `drop` → переход статуса; `dragend` → сбросить состояние.
- Обновление **оптимистичное**: карточка сразу в новой колонке, затем `POST …/transitions`;
  при ошибке — вернуть назад + тост.
- Клавиатурная альтернатива обязательна: transition-кнопки в карточке задачи.
- Библиотека по умолчанию — `@dnd-kit/core`.

### 5.4 Filtering
Фильтры комбинируются по AND: `type` + `assignee` + текстовый `q` (по `summary`,
`issueKey` и `description`, case-insensitive). «Clear» показывается только когда что-то
активно. Счётчик «X of Y» — всегда. Серверные фильтры (`status`, `assigneeId`, `labelId`)
отдавать в `GET /issues`.

**Поиск двухслойный, и слои отвечают на разные вопросы (TAS-179).** Поле остаётся
локальным и мгновенным — оно фильтрует загруженную страницу и рисует результат на
первом же символе. Под ним, от трёх символов и с debounce §4.14, живёт
`GET /issues/search`, ограниченный текущим проектом. Он нужен ради двух вещей, которых
локальный слой дать не может: честного `totalCount` — `issues.length` считает одну
страницу и перестаёт быть числом задач проекта после сотни — и совпадений, которых на
этой странице нет.

Серверные попадания показываются **отдельной группой под колонками, а не в колонках**:
`IssueShortResponseDto` не несёт `status`, и карточка, положенная в колонку статуса,
была бы утверждением, которого сервер не делал. Группа не участвует в drag-and-drop по
той же причине.

Геометрия группы: `max-height:38vh` с прокруткой, фон `--surface-2` (утопленная
плоскость §2.1), `padding:13px 18px`, верхняя граница `1px --border`. Сетка —
`repeat(auto-fill, minmax(312, 1fr))`, `gap:14`: минимум колонки и шаг доски (§4.9,
§2.4), растянутые по ширине. Именно `1fr`, а не фиксированные 312: полоса тут уже
колонок доски, и совпадать будет только левый край — измерено, на 1280 колонки идут с
шагом 326, карточки с шагом 416. Это сознательный выбор в пользу заполнения полосы, и
«восстановить шаг» фиксированной дорожкой значит получить рваную сетку, думая, что
документ этого требует. Карточка — `radius:11`, `padding:10px 12px`, `--surface`,
`--shadow`. Шапка — `strong` 12.5/650 плюс одна строка 11.5 `--fg-2` с
`max-width:560`. Пятьсот шестьдесят — значение этой секции, а не цитата из §2 (там
таблица размеров и правила меры чтения нет). Одна строка, не две: объяснять читателю,
почему попадания лежат не в колонках, — это рассказывать ему про наше устройство
вместо его данных (§1). Потолок 38vh связывает только на телефоне — на 390 это 320.7
из 844 — и там он и нужен, чтобы колонки не исчезли под результатами. Запрос страницы
— 50 попаданий.

`Y` ждёт, а не мигает: пока debounce не догнал поле, две половины счётчика измеряют
разные запросы, и «8 of 3» — это не редкость, а то, что получается по умолчанию. В
этот промежуток `Y` — `PendingValue` (§5.6), карточки — нет. При активном фильтре по
метке серверный слой выключается целиком: у ручки нет `labelId`, и она отвечала бы на
более широкий вопрос, чем задаёт бар.

### 5.5 Inline editing
Заголовок и описание задачи редактируются на месте (без «режима правки»): изменение → локальный
стейт сразу → `PATCH` с debounce 600ms → в ленте активности появляется событие. Ошибка → откат
значения + тост.

### 5.6 Empty / loading / error
- **Loading:** скелетоны формой конечного элемента (карточки колонок, строки списка), фон
  `--surface-2`, пульсация `opacity .35→1`. Спиннеров в контенте не использовать.
- **Empty:** одна строка 11.5–12px `--fg-3` в пунктирной рамке (колонка) или короткий текст +
  primary-действие (список проектов). `--fg-3` — пока строка действительно мета рядом
  с чем-то; когда она **единственное содержимое экрана** (пустой результат фильтра
  проектов), она берёт `--fg-2`: §7 выводит из-под порога только некритичную мета, а
  единственный текст на экране таковой не является. Записано здесь, потому что раньше
  исключение жило комментарием в CSS — то есть код правил документом в обход порядка
  авторитетов.
- **Error:** тост снизу справа: `background:var(--surface); border:1px var(--border);
  radius:11; box-shadow:var(--shadow-pop)`, текст 12.5px, акцент-полоса/иконка `--danger`.
  Показывать `error.message`, `error.requestId` — мелким `--fg-3` (копируемым).

> **Пробел (TAS-140).** Тост-компонента в коде нет. Ошибки показываются только инлайном
> (`.form-error` на формах логина и создания задачи), а `requestId` не доходит до
> пользователя вообще. Это значит, что откаты оптимистичных мутаций (§5.3, §5.5) сейчас
> происходят молча: карточка возвращается в исходную колонку без единого объяснения.
> Требование выше — правильное, поэтому оно оставлено как есть, а не подогнано под код.
> Спецификация тоста — контракт для будущей реализации, а не описание текущего состояния.

### 5.7 Permissions
Роль берём из `GET /projects/{id}/membership`. `VIEWER` — только чтение: скрывать «New»,
transition-кнопки, Delete, drag (`draggable=false`), инлайн-редактирование (readOnly),
composer комментариев.
Не полагаться только на скрытие — сервер всё равно проверяет.

Комментарии гейтятся **двумя** правилами, не одним: создание — по роли
(`ADMIN`/`MEMBER`), редактирование и удаление — по авторству (`comment.authorUserId ===
currentUser.id`). Роль `ADMIN` не даёт права править чужой комментарий.

> **Внимание при проверке прав.** В режиме `hybrid` с
> `VITE_TASKA_ASSUME_PROJECT_ADMIN=true` роль синтезируется на клиенте и всегда `ADMIN`
> (см. §6, «Режимы API» и `docs/ai/API-DIVERGENCE.md`). Прошедшая в этом режиме проверка
> ролевого гейтинга не доказывает ничего: `VIEWER` в нём просто недостижим.

### 5.8 Раздел администрирования
`/admin` — не экран, а собственная область с разделами. Она остаётся внутри
общего app shell (§5.1): топбар тот же, меняется только тело.

**Разделы и маршруты.**

| Раздел | Route | Состояние |
| --- | --- | --- |
| Data | `/admin/data/:service?/:table?` | работает; строка по ключу — `…/:table/:id` (TAS-161) |
| Events | сводка `/admin/events`, журнал `/admin/events/outbox/:service?`, строка — `…/:id` | работает (TAS-167); бэковая половина retry влита (PR backend#143), фронтовая — [TAS-194](https://jira.ozero.dev/browse/TAS-194) |
| Users | `/admin/users` | работает (TAS-186); три ручки записи задеплоены — бэковый PR #146 (TAS-107 + TAS-108) влит 2026-09-07, замер 2026-09-08 (TAS-196) |
| Audit | `/admin/audit` | заглушка §4.19 до TAS-160 |

`/admin` без хвоста редиректит в `/admin/data`. Разделы рисуются **все**, включая
незаполненные: структура раздела — это тоже информация, и админ, который видит
Audit заглушкой, знает о нём больше, чем админ, который не видит ничего.
Гейт `globalRole = GLOBAL_ADMIN` стоит один раз на всей области (§4.18, §5.7);
сервер остаётся авторитетом на каждой ручке.

**Состояние — в URL, не в React.** Выбранные сервис, таблица и строка живут в
маршруте, страница и фильтр — в query. Админская работа состоит из «посмотри вот
на это»: ссылка на конкретную таблицу должна открываться у другого админа и
переживать перезагрузку. Это же снимает старое поведение, где первая таблица
каталога подставлялась молча, — теперь подстановка видна в адресе.

**Шапка области.** Над телом раздела: крошка «Administration ›» 11.5/550
`--fg-2` и следом имя раздела (22/700 `--fg`). Обе части — **внутри одного
`h1`**: причина, по которой крошка существует, ровно так же верна в дереве
доступности, а соседний `<p>` оставил бы заголовок с именем «Data». Область
называет себя, а не только текущий раздел: «Data» без контекста читается как
ещё один экран продукта.

Справа — маркер `read-only`: 10.5px моно `--fg-2` (не `--fg-3`: тот даёт 2.8:1
на этой плоскости, а это утверждение, а не украшение), рамка `1px --border`,
`radius:6`, `padding:2 7`. Он не украшение и не статус запроса. **Свойство
раздела, а не области**, и это уже подтвердилось: Users с TAS-186 пишет и
маркера не несёт, Data и Events читают и несут, а retry принесёт
[TAS-194](https://jira.ozero.dev/browse/TAS-194) и снимет маркер с Events одного
(бэковая половина — TAS-106, PR backend#143, влита 2026-09-03). У
разделов-заглушек маркера нет вовсе —
раздел, который ничего не делает, не может осмысленно заявлять, что только
читает.

**Рельс разделов.** Слева, ширина 168, фон `--surface`, правая граница
`1px --border`. Пункт: иконка 15 + текст 12/600, `padding:6 9`, `radius:8`,
в покое `--fg-2`, hover — `--surface-2` + `--fg`, активный — `--surface-2` +
`--fg` + `aria-current="page"`. Внизу, за разделителем, выход в `/projects`
(`--fg-3`). Отдельной кнопки «Back to projects» под контентом больше нет: выход
из области принадлежит области, а не последнему её экрану. Логотип в шапке
(§4.13) ведёт туда же и рельсе не противоречит: это выход из **оболочки**,
одинаковый на всех экранах с сессией, тогда как выход в рельсе принадлежит
разделу и стоит там, где читатель уже выбирает раздел. На ширине < 900 они
видны одновременно, и это приемлемо — дублируется цель, а не элемент
управления. На ширине < 900
рельс схлопывается в горизонтальную полосу над контентом.

**Data: колонка каталога.** Вторая колонка, ширина 200, фон `--bg`: поле поиска
(§4.14, 26px) и под ним список, сгруппированный по сервису — заголовок группы
10.5px `--fg-3` uppercase, пункт таблицы 11.5px моно, активный — `--surface-2` +
`--fg`. Плоский ряд чипов, который был здесь до TAS-159, держал четыре таблицы и
ломался на десяти; шесть сервисных БД дают три-четыре десятка. Поиск фильтрует
по имени таблицы и сервиса, пустой результат — строка «Nothing matches» 11.5px
`--fg-3`.

**Data: таблица.** Плотность выше продуктовой — это чтение сырых строк, а не
работа с задачами:
- строка 30, `padding:6 10`, базово 11.5 UI-шрифтом;
- моно (§2.3, 11.5/500, `tabular-nums`) — **только** для значений, которые
  сравнивают глазами по вертикали: id, временные метки, числа, JSON, имена
  сервисов и таблиц. `email`, `display_name` и прочая проза остаются UI-шрифтом.
  Моно на всей таблице было бы «атмосферой», а её `docs/ai/REFERENCE-LOCK.md`
  запрещает прямым текстом; выравнивание колонки идентификаторов — это работа,
  а не атмосфера, и различие проходит ровно по типу колонки из каталога;
- шапка `position:sticky; top:0`, фон `--surface-2`, текст 11/600 `--fg-2`;
- колонка primary key примораживается слева (`position:sticky; left:0`) с
  правой границей `1px --border` — при горизонтальном скролле строка обязана
  оставаться опознаваемой;
- **значение primary key длиннее 12 символов обрезается до первых 8** и несёт
  полное значение в `title` и в accessible-имени, а по клику копируется целиком.
  Подтверждение — двухсекундная подсветка самого ключа плюс визуально скрытый
  live-region, а **не** надпись рядом, как у Request ID: там подпись ничего не
  двигает, а здесь «Copied» расширяла примороженную колонку на 45px и дважды
  сдвигала всю таблицу, ради которой колонку и примораживали. Отказ буфера
  говорит «Couldn't copy» — молчание неотличимо от мёртвой кнопки.
  Примороженная колонка имеет смысл, пока она узкая: полный uuid
  в 36 символов делает её самой широкой в таблице и выталкивает остальные
  колонки за край — ровно та беда, из-за которой раздел и переделывался.
  Короткий ключ (числовой id, короткий код) не трогаем;
- контейнер скролла несёт `tabindex="0"` и `aria-label` (§7): без этого таблица,
  у которой нет сортируемых колонок, не скроллится вбок с клавиатуры в Safari и
  Firefox вообще;
- **sensitive-колонка — это теперь три случая, а не один** (TAS-104). Маскирует
  сервер, и делает это тремя способами, а каталог сообщает только
  `sensitive: true` — какой способ достался колонке, видно исключительно по
  пришедшему значению. Ключа в строке нет (`HIDE`) или значение равно `***`
  (`MASK_FULL`) — иконка замка + `hidden` `--fg-3` в ячейке; до читателя не
  дошло ничего, и это единственное, что замок **в ячейке** отныне означает.
  Значение со звёздочками (`MASK_PARTIAL`) печатается как пришло: `n****a@mail.ru`
  отвечает на вопрос «чей это ящик», а замок поверх него не отвечает ни на что —
  ровно ради этого ответа частичную маску у бэкенда и просили;
- **замок никуда не делся, а переехал в шапку колонки** — и в метку поля на
  карточке. Он свойство колонки, а не ячейки, поэтому говорится один раз, а не в
  каждой строке; без него `a*****ample.com` читался бы как хранимое значение. В
  шапке он берёт `--fg-2` по наследству, а не `--fg-3`: на `--surface-2` в
  светлой теме `--fg-3` даёт 2.76:1 при пороге §7 в 3:1, а на колонке с
  частичной маской этот значок — единственное, что отличает звёздочки от данных,
  и служебным цветом он поэтому не красится;
- **«никогда длину значения» остаётся правилом, но адресовано оно теперь
  серверу.** Оно писалось, когда клиент был единственным, что стоит между
  читателем и значением. Сейчас решает сервер, и для `MASK_PARTIAL` он длину уже
  раскрыл — она в теле ответа, в кэше react-query и в devtools независимо от
  того, что нарисовано на экране. Клиенту запрещено раскрывать **больше**
  сервера: дорисовывать длину, восстанавливать маску, показывать `***` как
  данные;
- fail closed теперь в обе стороны: правило по-прежнему из каталога и при
  отсутствии записи в каталоге таблица не показывается вовсе, а вдобавок
  значение sensitive-колонки печатается, только если несёт след маскировки —
  звёздочку. Колонка, пришедшая открытым текстом вопреки каталогу, прячется:
  каталог сказал, что там секрет, а хеш, попавший на экран, обратно не вернуть;
- `null` — `—` `--fg-3`. Прочерк на месте пустого значения — это служебный
  знак, а не данные, и по §1 он не имеет права весить столько же, сколько
  содержимое соседней строки;
- строка кликабельна и ведёт на `…/:id` — карточку строки. Три условия, все
  обязательные: каталог назвал primary key, его тип — `uuid`, и колонка ключа
  не помечена sensitive. Первые два — про гейтвей, который принимает `id`
  именно как UUID, поэтому строку с числовым или текстовым ключом адресовать
  нечем. Третье — про сам адрес: ключ входит в URL, а с ним в адресную строку,
  в доступное имя ссылки и в историю браузера, так что ссылка на строку с
  секретным ключом напечатала бы ровно то значение, которое таблица только что
  отказалась показать. Не выполнено любое — строка не кликабельна и не
  притворяется: ссылка, которая гарантированно приводит к отказу или к утечке,
  хуже её отсутствия;
- **клавиатурный путь — отдельная ссылка в последней ячейке строки**, а не сама
  строка: `<tr>` не может быть контролом, и «кликабельная строка» без этого
  означала бы раздел, проходимый только мышью. Цель не меньше 28×28 (§7),
  фокус — `focus-visible` с отступом 2px, и **строка в фокусе подсвечивается
  так же, как при наведении**. Последнее не косметика: на широкой таблице
  ссылка уезжает за правый край контейнера скролла, и без подсветки строки
  клавиатурный читатель видит кольцо, но не видит, к какой строке оно
  относится.

**Data: карточка строки.** `…/:table/:id` — не модалка, а тело раздела вместо
таблицы: адрес обязан открываться прямой ссылкой у другого админа, а модалка,
восстановленная из URL, приезжает поверх пустоты. Рельс и колонка каталога
остаются на месте — читатель не вышел из таблицы, он смотрит одну её строку.

- шапка карточки: имя таблицы 12/600 и под ним значение ключа целиком,
  11.5 моно с копированием по клику (подтверждение — как в §5.8 для ключа в
  таблице). Здесь ключ показывается **полностью**: обрезка до 8 символов
  существует ради ширины примороженной колонки, а карточка — то самое место,
  куда идут за полным значением;
- поля — список пар: имя колонки 11/600 `--fg-2` слева колонкой ширины 200,
  значение справа. Значение подчиняется тому же правилу шрифта, что и ячейка
  таблицы: моно с `tabular-nums` для id, времени, чисел и JSON, UI-шрифт для
  прозы. Значение не обрезается и переносится — на карточке нет соседних
  колонок, которые обрезка защищала бы;
- `null` — `—` `--fg-3`, как в таблице; sensitive-колонка — те же три случая и
  то же fail closed, что в таблице, но замок здесь **только** в метке поля:
  метка и значение стоят одно под другим, и два одинаковых замка в 38 пикселях
  друг от друга читаются как заикание, а не как два разных утверждения. Значение
  несёт один курсивный `hidden` `--fg-3`. В таблице замок в ячейке остаётся —
  там метка колонки далеко, в примороженной шапке;
- ширина карточки ограничена 860. Метка занимает 200, самое длинное значение —
  около 300, и без ограничения на 1920 разделители тянутся через тысячу
  пустых пикселей. Ограничение читаемой полосы — общее правило продукта (§2.7),
  а не исключение для этого экрана;
- имя таблицы и ключ повторяются: в ссылке назад и в шапке, в шапке и в поле
  `id`. Это сознательно. Шапка — адрес строки, список полей — сама строка
  целиком, и выбросить из него колонку ключа значило бы, что список врёт о том,
  из чего строка состоит. Цена — два повтора; альтернатива — список, про
  который надо помнить, что одна колонка из него изъята;
- назад — ссылка «‹ `service.table`» над карточкой. Переход из строки уносит
  query таблицы (`page`, `sort`, `filter`) в адрес карточки, и ссылка назад
  возвращает ровно ту страницу и тот фильтр, из которых читатель пришёл.
  Без этого возврат из строки на 7-й странице отправлял бы на первую.
  Доступное имя — «Back to `service.table`», а не одно имя таблицы: шеврон
  `aria-hidden`, и без подписи ссылка звучит ровно как заголовок карточки
  тридцатью пикселями ниже — два одинаковых слова, ни одно из которых не
  сказало, что это выход;
- строки, которой нет, сервер отвечает 404. Это не §4.18: адрес раздела верен,
  отсутствует конкретная строка — «No row with this key in `service.table`»
  внутри карточки, рельс и каталог остаются рабочими.

**Data: фильтр.** Кнопка-чип «+ Filter» открывает поповер (§4.12) с тремя полями
column / match / value. Применённый фильтр показывается чипом
`column match value` с крестиком; кнопка «Clear» отдельной строкой не нужна.
Форма из трёх подписанных селектов в ряд, которая была здесь раньше, занимала
полосу шириной с экран ради одного фильтра — а больше одного контракт и не даёт.

Чип обрезается по ширине, и тогда на нём действует то же правило, что и на
ключе в таблице: полное значение обязано остаться и в `title`, и в доступном
имени. Обрезка, после которой значение негде прочитать целиком, — это потеря
данных, а не экономия места. Фильтр с пустым значением не применяется и чипа не
создаёт: чип, который читается как применённый, над нефильтрованной таблицей —
худший из возможных ответов, и от него не спасает то, что запрос ушёл честным.

Набор операторов зависит от типа колонки из каталога, и это не удобство, а
единственный способ не отправить запрос, который сервер отвергнет: гейтвей
проверяет совместимость сам и отвечает 400. `contains` — только текстовые
колонки, `from`/`to` — временные и числовые, `is` — любые. Оператор, потерявший
смысл при смене колонки, сбрасывается в `is`, а не остаётся выбранным в селекте,
где его опции уже нет. Когда тип колонки допускает **единственный** оператор —
а это частый случай, `uuid`, `inet` и `boolean` все дают только `is` — Match
рисуется статическим текстом 11.5 `--fg-2` на месте селекта, а не селектом с
одним пунктом: выпадающий список, который не может ничего изменить, притворяется
выбором.

Значение тоже ограничивается типом, и по той же причине: сервер разбирает его
типизированно и отвечает 400. Числовая колонка получает числовое поле, булева —
выбор `true`/`false`, временная — датапикер. Свободное текстовое поле остаётся
только там, где сервер и правда принимает произвольную строку.

**Время в этом разделе — UTC, и поле обязано это сказать.** Датапикер читается
как UTC, а не как локальные часы, и подписан «UTC» — потому что UTC на проводе,
а не потому, что так сегодня выглядит колонка. Разница существенная: таблица
печатает то, что отдал сервер, и если какой-нибудь сервис однажды вернёт
временную колонку с другим смещением, обоснование «в таблице же `Z`» исчезнет, а
пикер молча станет неверным ровно тем способом, которым только что перестал.
Колонка с не-`Z` смещением — это изменение контракта, которое поднимают, а не
деталь отображения, которую всасывают.

Без подписи админ, глядя на колонку с `08:00:00Z`, вводит 08:00 и получает
фильтр на три часа раньше — цифры, которые он набрал, и цифры, по которым идёт
отбор, разъезжаются молча. На проводе — полный ISO-8601
со смещением и **без миллисекунд** (`2026-01-01T00:00:00Z`): сервер парсит
строго, `2026-01-01` и `2026-01-01T00:00` — уже 400, а `.000` ничего не
добавляет и съедает четверть ширины чипа. Формат — работа формы, а не то, что
админ обязан помнить.

**Пагинация** — в футере таблицы, `position:sticky; bottom:0`, фон `--surface-2`,
не отдельным блоком под ней. Футер показывается **всегда**, даже когда страница
одна: «Page 1 of 1» — это ответ на вопрос «я вижу всё?», а таблица, у которой
футер то есть, то нет, каждый раз меняет высоту рабочей области. Кнопки при
одной странице просто выключены.

**Ошибки.** Четыре случая различаются словами, а не одним текстом: отказ
сервера (403/404), **отвергнутый запрос (4xx)**, ошибка сервера (5xx) и
недоступность. Четвёртый случай — это «мы не дозвонились», и всё, что попадает
в него по недосмотру, читается как авария инфраструктуры: раздел уже один раз
называл так пятисотку, и с приходом типизированной валидации на гейтвее
четырёхсотка стала штатным ответом на плохой ввод, а не редкостью. Рядом с
заголовком печатается текст самого сервера — он называет колонку и то, что с
ней не так, и это единственная часть, которая говорит читателю, что именно
исправить. `X-Request-Id` показывается только в этой области — здесь он у
единственного читателя, который пойдёт с ним в лог гейтвея — и **копируется по
клику** (иконка копирования 14, подтверждение «Copied» 11px `--fg-3` на 2с).

**Область desktop-first, и это сказано вслух.** Раздел читают с рабочей машины;
на телефоне он остаётся достижимым, но не оптимизированным: рельс сворачивается
в горизонтальную полосу (<900), каталог уезжает над таблицей (<720), и цели
касания там 26–29px против 44 из §7. Это осознанная граница, а не забытая
работа. Что действительно нужно сделать при первой же необходимости работать с
телефона — превратить каталог в раскрывающийся список с триггером из имени
таблицы, чтобы строки получали весь экран; пока этого нет, нижний край списка
закрыт маской-затуханием, и это заплатка, а не решение. Рецепт маски здесь —
исторический: с TAS-186 по умолчанию берётся самозакрывающаяся пара слоёв
(см. «Users» ниже), и когда до этого края дойдут руки, он переедет на неё.

> `GET /readonly/{service}/{table}` отвечает 200 (проверено на

> `primaryKey` (`id:uuid` у `outbox_events`), строки адресуемы. Раздел Data

**Events.** Диагностика transactional outbox (TAS-167): что застряло, где и
насколько давно. Два вида под одной шапкой раздела: **Problems** — сводка
проблемных событий по всем сервисам разом, и **Outbox** — журнал таблицы
`outbox_events` одного сервиса со всеми фильтрами. Открывается раздел сводкой:
в Events приходят с вопросом «что сломалось», и счётчики отвечают на него до
первого клика; журнал — инструмент разбора, в него уходят, уже зная, что
искать. Правило §5.8 про state в URL действует без изъятий: вид, сервис,
страница, сортировка и каждый фильтр живут в адресе.

Переключатель видов — segmented control (§4.2) из двух `NavLink` под шапкой
раздела, `aria-current="page"` у активного. Это навигация, а не состояние:
вид — часть адреса. `/admin/events` — сводка; редиректа нет, сводка и есть
корень раздела.

**Events: сводка (Problems).** `GET /readonly/outbox/problematic-summary` без
параметров: счётчики всегда по всем сервисам, список — до лимита бэка (по
умолчанию 100), от самых старых к новым. Пагинации нет и не будет: если
проблемных больше сотни, это повод чинить, а не листать; полный разбор — в
журнале с фильтром, где пагинация в базе.

- **Матрица счётчиков** — главное содержимое вида: строки — сервисы из
  `counts` ответа (не из каталога: считает бэк, и его список — истина),
  отсортированные по ключу сервиса на клиенте: порядок в ответе не
  специфицирован — бэк собирает счётчики по сервисам конкурентно, и матрица,
  тасующая строки между двумя рефетчами, была бы хуже любого фиксированного
  порядка. Это сортировка представления, не данных: у списка событий порядок —
  семантика ручки, у строк матрицы семантики порядка нет. Колонки — три
  категории. Подписи: «Failed» (исчерпаны попытки), «Stuck
  processing» (просрочен таймаут обработки), «Overdue NEW» (шедулер не
  забрал). Значение — моно `tabular-nums`; ноль — `--fg-3`, не ноль — `--fg`
  600. Ноль не красится успехом и не-ноль не красится аварией: цифра 3 в
  колонке Failed — уже сообщение, красный поверх него — украшение (§1).
- **Список** — строки, как отдал сервер, в его порядке. Клиент не
  пересортировывает: порядок — семантика ручки (старейшие показывают, когда
  началось), и клиентская сортировка врала бы о том, что сервер отрезал.
  Колонки: сервис, категория, возраст, event type, aggregate type, aggregate
  id, status, attempts, last error message. Колонка сервиса примораживается
  слева, как ключ у Data-таблицы: список шире плоскости, а при
  горизонтальном скролле строка обязана оставаться опознаваемой — «где» и
  есть ответ этого вида. Возраст — **длительность от `created_at`**, не
  календарное слово: `25h ago`, `3d ago` (минуты до часа, часы до 48 часов,
  дальше дни), полный UTC — в `title` и в доступном имени. Продуктовый
  календарный голос («Yesterday») здесь не годится: колонка набрана моно с
  `tabular-nums` ровно затем, чтобы значения сравнивались глазами по
  вертикали, а «Yesterday» не сравнивается с «15h ago» и накрывает 12–36
  часов именно на верхней строке — той, ради которой список отсортирован от
  старых. В комментариях, уведомлениях и мете карточек календарный голос
  остаётся как есть. Категория выводится из `status`
  (FAILED → Failed, PROCESSING → Stuck processing, NEW → Overdue NEW), а не из
  `reason`: `reason` — человекочитаемая строка бэка, и парсить её — значит
  сделать контрактом то, что им не является. Целиком серверная фраза живёт на
  ячейке категории — в `title` и в доступном имени: видимое слово —
  категория, полное предложение бэка — при наведении и у скринридера. Не
  колонкой — три предложения дословно повторяют три категории и платят за это
  шириной списка; и не в карточке — карточка рисует колонки таблицы из
  каталога, а `reason` — поле сводки, не колонка, и по прямой ссылке на
  строку его просто не существует. Неизвестный `status` рисует сырое значение
  без категории, `reason` при нём остаётся в `title` — и ничего не роняет.
- **`notAllShown`** — строка над списком: «Showing the oldest N events; the
  counts above cover the rest.» 11.5 `--fg-2`. Не alert: обрезка — штатное
  поведение ручки, а не ошибка.
- **Пустая сводка** — матрица с нулями остаётся (она и есть ответ), на месте
  списка — «No problematic events.» `--fg-2` (не `--fg-3`: тот даёт 2.91:1 на
  `--bg` в светлой теме против порога 3:1 из §7 — довод, уже закрепивший
  `--fg-2` за `.admin-note` на этой же плоскости). Прятать матрицу нельзя:
  «всё хорошо» с цифрами — утверждение, без цифр — заставка.
- Строка кликается в ту же карточку события, что и журнал, — отдельной
  ссылкой в последней ячейке, по правилам Data-таблицы, — и карточка
  возвращает в сводку.

**Events: журнал (Outbox).** Generic-грид §5.8 на таблице `outbox_events`
одного сервиса: `GET /readonly/{service}/outbox_events` с пагинацией, той же
маскировкой, теми же ошибками и тем же fail closed. Всё, что умеет таблица
Data, журнал наследует, потому что это она и есть; ниже — только отличия.

- **Селектор сервиса** — segmented control в шапке плоскости; только сервисы,
  у которых в каталоге есть таблица `outbox_events` (сегодня auth, project,
  issue). Из каталога, не хардкодом: появится outbox в новом сервисе —
  сегмент появится сам. `/admin/events/outbox` без сервиса редиректит в
  первый по каталогу, подстановка видна в адресе (как у Data). Смена
  сервиса — навигация путём, и query **переживает её**, кроме страницы
  (сбрасывается в 1): таблица та же, колонки те же, и «покажи FAILED в auth,
  а теперь в project» — прямое назначение селектора. Data при смене таблицы
  query сбрасывает, но там меняются колонки; здесь причина сброса не
  существует, и наследовать его было бы карго-культом.
- **Сортировка по умолчанию** — `created_at` по убыванию: журнал читают с
  конца. Голый адрес значит именно это, а не «как сервер решит»; явный sort
  в query появляется, когда читатель выбрал иное.
- **Фильтры** — не колонка/оператор/значение, а девять именованных фильтров,
  которые этой таблице действительно нужны (TAS-167): Status is (select из
  NEW / PROCESSING / PUBLISHED / FAILED), Event type is, Aggregate type is,
  Aggregate id is, Request id is, Created from, Created to (оба — UTC с
  подписью, формат провода — полный ISO-8601 без миллисекунд, как выше),
  Error contains, Attempts ≥. Поповер «+ Filter» (§4.12) предлагает список
  фильтров, а не список колонок: оператор в каждом уже решён, и селект
  match, у которого нет выбора, не рисуется вовсе — по той же причине, по
  которой Data ставит статический текст вместо селекта с одним пунктом.
  Применённые фильтры — чипы с крестиком, как у Data, любые вместе, но
  каждый ключ не больше одного раза: контракт читает дубль ключа как одно
  значение, и UI не предлагает того, что провод не повезёт. Мультиселекта по
  статусу нет — ограничение контракта, поднято в TAS-167, на клиенте не
  изобретается. `payload` не фильтруется и не предлагается: `jsonb` на бэке —
  категория OTHER, без `contains` и диапазонов.
- В остальном — Data-таблица как есть: примороженный ключ, сенситив-правила,
  строка в карточку, футер с пагинацией.

**Events: карточка события.** `…/outbox/:service/:id` — карточка строки §5.8:
тот же компонент, те же правила полей, `null` и сенситива, с одним новым
правилом, которое достаётся и Data. Значение колонки типа `jsonb`,
разобравшееся как JSON, печатается развёрнутым, с отступами (`pre`, моно,
перенос строк); не разобравшееся — печатается как пришло, без починки на
клиенте. «Как пришло» — осознанно, и правило пережило случай, который его породил.
Битый формат `JsonByteArrayInput{…}` — дефект admin-service — не парсился и
потому оставался виден; **починен и задеплоен, замер 2026-09-08: двадцать
строк, каждый payload — чистый JSON**. Правило остаётся, потому что оно не про
тот дефект, а про следующий: маскированный payload — валидный JSON со
звёздочками в значениях — рисуется им же без особого случая, а неразобравшееся
значение любого происхождения остаётся видимым вместо тихо починенного.
Срезать java-префикс руками было запрещено (TAS-167) ровно поэтому: он ушёл с
фиксом на бэке, а клиентская починка пережила бы его молча и скрыла бы
следующий.

**Events: повтор события (TAS-194).** У строки в Problems есть одно действие —
повторить. Оно построено по образцу подтверждения в Users (§5.8 ниже), а не
изобретено заново: причина обязательна и уходит в аудит, submit заперт, пока
она пуста, счётчик остатка виден, диалог остаётся открытым на отказе.
Единственное отличие в числе — предел причины здесь **1000** символов, а не 550;
это два разных места контракта, а не забывчивость.

Три вещи, которые диктует сервер и о которых экран обязан говорить вслух:

- **Кнопка есть не у всякой проблемной строки.** Ручка принимает `FAILED` и
  `PROCESSING`, но не `NEW` и не `PUBLISHED` — а «Overdue NEW» это одна из трёх
  категорий, которые Problems и показывает. Правило §5.8 «одна кнопка или ни
  одной» здесь работает буквально: у строки, которую сервер откажется
  повторять, действия нет вовсе. Нарисовать её и получить 400 значит выдать
  свой выбор за отказ пользователю.
- **Порог у сводки и у повтора разный.** Сводка называет `PROCESSING`
  застрявшим через пять минут, повтор принимает через десять, обе величины —
  серверная конфигурация, на провод не выходит. Поэтому на строке `PROCESSING`
  стоит предупреждение *до* нажатия, а клиентских часов нет: зашить десять
  минут значило бы угадать конфигурацию стенда (`API-DIVERGENCE.md`,
  [TAS-200](https://jira.ozero.dev/browse/TAS-200)).
- **`attempts` не сбрасывается.** Это самое соблазнительное неверное
  предположение об этой ручке, поэтому число названо в предложении перед
  кнопкой: у события шесть попыток и после повтора будет шесть.

И одно про отказ: запись в аудит идёт после коммита обновления, поэтому 5xx
может прийти вслед за удавшимся повтором. Формулировки `server` и
`unreachable` это признают — событие могло быть повторено; `conflict` говорит
обратное и имеет право, потому что пригодность проверяется и до обновления, и
в его собственном `WHERE`.

С этим действием раздел Events перестаёт быть read-only и теряет маркер §4.x —
маркер это свойство раздела, а не области.

Назад из карточки — к тому, откуда пришли: из журнала — с query журнала (как
у Data), из сводки — в сводку. Откуда пришли — часть адреса карточки, не
history: прямая ссылка и перезагрузка обязаны дать тот же «назад».

**Users.** Учётные записи всего инстанса и **единственное место в области,
которое пишет** (TAS-186). Список — не собственная ручка, а `auth.users`,
прочитанная тем же generic-ридом `GET /readonly/{service}/{table}`, что и
таблицы Data; отличие в том, что колонки здесь **названы**, а не нарисованы
все подряд: раздел знает, на что смотрит.

- **Ни фильтра, ни сортируемых заголовков**, и это замер, а не упрощение: на
  задеплоенном гейтвее у этой таблицы `meta.filterableColumns` и
  `meta.sortableColumns` пусты (2026-08-25), поэтому и чип «+ Filter», и
  кликабельная шапка отправили бы запрос, который сервер отвергнет. Появятся в
  каталоге — появятся и здесь.
- **Колонки:** person (имя UI-шрифтом 12/550 и адрес под ним 11 `--fg-2` — это
  не мета: двое могут делить отображаемое имя и не могут делить почту), login
  (моно, §5.8), global role, status, и ячейка действия. `null` — `—` `--fg-3`,
  как везде в области.
- **Строка 42, не 30.** Пол §5.8 писался для грида сырых значений; здесь первая
  ячейка несёт две строки, и 42 — это ровно они при `line-height 1.3` плюс те же
  `padding:6 10`. Плотность и кегль остаются §5.8-шными.
- **Ширина полосы — 860**, как у карточки строки и по той же причине: набор
  колонок здесь конечный и известный, а без ограничения на 1920 человек
  оказывается у одного края, а единственная кнопка — у другого.
- **Статус и роль — пилюли §4.5** в геометрии label-чипа (height 20, radius 20,
  11.5/600), не 28-пиксельной статус-пилюли панели: та выше ячейки, в которой
  стоит. Цвет несёт смысл и ничего не украшает (§1), и у раздела ровно три
  приёма, каждый со своим значением: **заливка** оттенком `--danger` — проблема,
  которую создал администратор; **край** — состояние, которое ещё не улеглось;
  **ничего** — норма. `BLOCKED` — заливка
  (`color-mix(in oklab, var(--danger) 14%, transparent)`): единственное
  состояние, которое кто-то назначил. `ACTIVE` — обычное состояние и остаётся
  тихим (`--surface-2` / `--fg-2`, 6.38:1 в светлой и 7.03:1 в тёмной).
  `INVITED` отличается **краем**, а не вторым оттенком — прозрачный фон и
  `1px dashed var(--border-strong)`, то же «ещё не здесь», что носит аватар без
  исполнителя (§4.4), и §7 не просит различать цветом. `LOCKED` (TAS-188)
  складывает два приёма, а не заводит четвёртый: оттенок `--danger` **на краю**,
  а не в заливке — сплошной `1px color-mix(in oklab, var(--danger) 45%,
  transparent)` против пунктира `INVITED`, глиф — тот же сдвиг 82/18 к `--fg`,
  что у `BLOCKED`. Рецепт записан здесь целиком по той же причине, что и у
  `BLOCKED`: правило в CSS должно быть проверяемо против документа, а не только
  против самого себя. Это проблема
  (оттенок), которую никто не назначал и которая пройдёт сама (край): аккаунт
  запирает сам себя после неудачных входов, и успешный вход его отпускает.
  Прочитать `LOCKED` как «его заблокировали» — ровно то недоразумение, которого
  раздел обязан избежать, и заливка сказала бы именно это.
  Текст `BLOCKED` — **не** голый `--danger`: по рецепту §4.5 он даёт 3.10:1 в
  светлой и 2.56:1 поверх подсвеченной строки, потому что тинт полупрозрачен и
  композитится с тем, что под ним. Смещение глифа на 18% к `--fg`
  (`color-mix(in oklab, var(--danger) 82%, var(--fg))`) даёт 4.21 / 5.43 в покое
  и 3.47 / 4.59 на подсветке — порог §7 держится во всех четырёх. Рецепт не
  придуман здесь: тем же живут пилюли меню профиля.

  **Мерить надо от той плоскости, на которой пилюля действительно лежит**, и
  это `--surface`, который красит `.admin-table-scroll`; `tr` и `td` над ним
  прозрачны. Не `--bg`: холст страницы — не плоскость этой пилюли, и замер от
  него занижает результат примерно на треть ступени и разошёл два ревью TAS-188
  между собой. Самая тесная плоскость **для этой пилюли** — не ховер строки, а
  22-пиксельная полоса-подсказка скролла у правого края (`--fg` 12% поверх
  `--surface`): с подсветкой строки поверх неё `LOCKED` даёт 3.21 в светлой.
  Самое тесное место таблицы — не здесь: на той же полосе `BLOCKED` даёт 3.36 в
  покое и **2.82 с подсветкой, то есть ниже порога §7**. Это старше TAS-188 и им
  не ухудшено, лежит в `docs/ai/BACKLOG.md` и чинится проходом по самой полосе,
  а не по каждой пилюле, которая её пересекает.
- **Неизвестный статус печатается дословно и не предлагает действия** (правило
  TAS-173) — и ничего не роняет. То же для строки, у которой таблица не дала
  ключа: адресовать нечем.
- **Ячейка действия — одна кнопка или ничего:** Block для `ACTIVE` и `INVITED`,
  Unblock для `BLOCKED`, Reset lockout для `LOCKED` (TAS-188). Третья кнопка не
  расширяет ячейку: строка по-прежнему предлагает ровно одну операцию, потому
  что сервер из каждого статуса разрешает ровно одну. Block из `LOCKED`
  запрещён (`ABORTED`), так что подставить там существующую кнопку значило бы
  нарисовать гарантированный отказ. Правила переходов — серверные, и клиент их повторяет,
  чтобы не рисовать кнопку с гарантированным отказом; правом это не является,
  сервер остаётся авторитетом (§5.7). Доступное имя — «Block <имя>», иначе
  семь кнопок в списке зовутся одинаково.

**Users: подтверждение.** Модалка §4.11. Она существует потому, что отменить
это читатель не может: разблокировка **не** возвращает приглашение.

- называет человека (имя, почта, `@login`) и переход в значениях сервера —
  `ACTIVE → BLOCKED`, моно; стрелка `aria-hidden`, для читалки — «from Active
  to Blocked»;
- **причина обязательна** для всех трёх операций, `maxLength` 550 (столько же
  принимает сервер, и ровно в одном месте — сгенерированный DTO гейтвея;
  `auth-service` и `admin-service` проверяют только непустоту), и
  пустая или из одних пробелов **не доходит до провода**: submit выключен, а
  строка под полем говорит почему. Как только причина есть, та же строка
  считает остаток символов. Объяснение стоит у поля, а не на кнопке: выключенная
  кнопка не получает фокус, и её `title` никто не прочитает;
- фразы добавляются, **только когда они верны**, потому что каждая — факт,
  который иначе неоткуда узнать: блокируется `INVITED` — «разблокировка сделает
  запись активной, приглашение не восстановится»; цель совпадает с текущим
  аккаунтом (`getCurrentUser`) — сказать прямо; Reset lockout — сказать, что
  аккаунт заперся сам после неудачных входов, что операция сбрасывает счётчик и
  возвращает статус `ACTIVE`, и — отдельно — что **пароль она не меняет**. Это
  первый вопрос администратора, и бэковая история (TAS-108) прямо выносит смену
  пароля за скобки, так что молчание прочиталось бы как «меняет». Клиентского запрета на второе
  нет и быть не должно: решает сервер, и правило у него одно — последнего
  активного глобального админа блокировать нельзя;
- `Esc` отменяет, `Cmd/Ctrl+Enter` подтверждает. Оба слушателя живут в самой
  модалке, а не в `Modal`: общий компонент их не несёт, и раздать их всем
  модалкам продукта — правка §7-долга (TAS-142), а не этой истории.

**Users: результат и отказ.** Оптимистичного обновления здесь **нет**, и это
осознанное отступление от правила AGENTS.md «мутации оптимистичны с откатом».
Оптимизм уместен, когда клиент способен предсказать ответ. Здесь он не
способен: «последний активный глобальный админ» — это счёт по всей таблице,
которого у клиента нет, а легальность перехода решает сервер. Нарисовать
переход заранее означало бы показать состояние, которое сервер откажется
принять, и откатить его на глазах — хуже, чем подождать. Поэтому кнопка ждёт.

- **Успех:** модалка закрывается, фокус возвращается на кнопку, которая её
  открыла, строка берёт статус, который назвал **сервер** (`currentStatus`, не
  то, что просили), подсвечивается на две секунды тем же рецептом, что и
  подтверждение копирования ключа, и визуально скрытый live-region говорит это
  словами («Nina Kowal is now active.»). Тоста в продукте нет — §5.6 держит
  этот пробел, — поэтому подтверждение живёт в самой строке. Следом список
  перечитывается: ответ ручки — мост на время рефетча, а не источник истины.
- **`changedAt` из ответа не рисуется нигде** — и довод здесь дважды
  переписан, потому что дважды опирался на неправду. Поле называется
  `changedAt`, а не `updatedAt`: так его ставит `AdminUserManagementMapper`
  гейтвея на голове бэкового PR #146, и так его объявляет `UserStatusResponseDto`
  (TAS-188). И «двое часов» — тоже неправда: `auth-service` собирает ответ как
  `.changedAt(savedUser.getUpdatedAt())` на сущности с `@LastModifiedDate`, то
  есть это **тот самый** `updated_at` строки `auth.users`, а не вторая отметка
  рядом с ним. Часы одни. Причина не рисовать остаётся, и она проще прежней:
  у раздела один источник значений — перечитанный список, — и поле из ответа
  на запись было бы вторым, живущим на две секунды дольше. Довод сознательно не
  опирается на то, что нарисовано:
  этот раздел печатает пять именованных колонок, и `updated_at` среди них нет,
  а раздел Data ту же таблицу показывает целиком. Правило должно держаться в
  обоих случаях.
- **Отказ оставляет модалку открытой** — закрыться поверх изменения, которого не
  произошло, было бы худшим из ответов, — и печатает таксономию §5.8 плюс один
  случай, который есть только здесь: отказ (403/404), **отвергнутый запрос
  (4xx)**, **конфликт**, ошибка сервера (5xx) и недоступность. Шестым здесь
  когда-то была «ручка ещё не задеплоена» — TAS-196 снял её в день, когда ручки
  задеплоились. Рядом — собственная фраза сервера («Cannot block the last active
  global admin») и `X-Request-Id`, который в этой области и зарабатывает своё
  место. Сентенции здесь свои, а не взятые у `AdminError`: та говорит про
  *чтение таблицы* и несёт кнопку «Try again», которая была бы вторым
  экземпляром submit'а строкой ниже.
- **Конфликт — не один статус, и это важнее, чем кажется.** Отказы бэкенда
  приезжают по-разному: «Cannot block/unblock user with current status: X» —
  это `ABORTED` и **409**, а «Cannot block the last active global admin» и
  «User is not in LOCKED status» — `FAILED_PRECONDITION` и **400**
  (`RestErrorMapper.mapGrpcCodeToHttpStatus`,
  `GatewayErrorHandler`, `DomainStatus` — прочитано на голове бэкового PR #146, влитого 2026-09-07, и перечитано на `develop` 2026-09-08 без изменений). То есть
  единственный отказ, который вообще умеет Reset lockout, приезжает **не** как
  409 — при том, что тест самого PR утверждает обратное, замеряя мок, а не
  путь. Тело ответа несёт имя
  gRPC-кода, поэтому конфликт распознаётся по **коду**, а не только по статусу;
  распознавание по одному статусу уронило бы главный отказ этой фичи в
  «отвергнутый запрос». Мок отдаёт те же два кода, поэтому предикат один на обе
  реализации.
- **«Не задеплоено» — не «пользователь не найден». Здесь это уже история, и
  правило пережило её.** Незамапленный путь падает в Spring'овый
  static-resource fallback и отвечает `404` с сообщением, которое начинается на
  `No static resource …` (замер 2026-08-25); задеплоенная ручка на 404 говорит
  `User not found` (а Reset lockout — ещё и `Credential not found`, тот же
  статус и тот же код при другом смысле). Читаются **обе** половины сразу —
  статус и подстрока. Половина «подстрока» измерена: без неё пропавший аккаунт
  прочитался бы как пропавший деплой. Половина «статус» не измерена и держится на
  другом основании: предикат обязан совпадать только с той сигнатурой, которую
  замерили, а совпадение по одному сообщению срабатывало бы на любом будущем
  ответе, где эта строка окажется, — например на 5xx. Такого ответа никто не
  видел; это довод не расширять предикат за пределы замера, а не описание
  наблюдения.

  Для этих трёх ручек шестая фраза снята: PR #146 влит 2026-09-07, и проба
  2026-09-08 с невалидным uuid в пути отвечает `400 INVALID_ARGUMENT` там, где
  раньше приходил static-resource `404`. Маршрут, который валидирует свой
  path-параметр, — замапленный маршрут. Абзац оставлен целиком, потому что сам
  предикат жив: `isUndeployedRoute` (`src/api/errors.ts`) обслуживает ручки
  вложений, чей бэковый PR #147 открыт, и панель вложений на доске читает им ту
  же пару статус-плюс-подстрока. Правило общее, снят только его пользователь
  здесь (TAS-196, закрытая запись в docs/ai/API-DIVERGENCE.md).
- **На телефоне колонка действия уезжает за правый край** контейнера скролла,
  как уезжает ссылка на строку у Data-таблицы, и достаётся тем же способом:
  контейнер сфокусирован, назван и скроллится с клавиатуры. Область
  desktop-first, и это сказано выше. Но здесь за краем остаётся **единственный
  орган управления раздела**, а на 390 таблица (443) приезжает в контейнер 360
  на `scrollLeft: 0` и без видимого скроллбара — то есть раздел читается как
  read-only, пока читатель случайно не свайпнет. Правый край поэтому несёт
  затухание.
- **Самозакрывающееся затухание — рецепт по умолчанию для этого продукта**, и
  выбор между ним и `mask-image` больше не бросается монеткой. Маска гасит
  край **вьюпорта** безусловно: докрутив до конца, читатель видит приглушённым
  ровно то, ради чего затухание и рисовалось, — здесь это была бы кнопка Block.
  Пара слоёв закрывается сама: верхний слой с `background-attachment: local`
  стоит у правого края **содержимого** и наезжает на нижний (`scroll`) ровно
  тогда, когда крутить больше некуда, а у таблицы, которая вовсе не
  переполняется, содержимое кончается на краю бокса — значит затухание не
  рисуется никогда и медиазапрос рецепту не нужен. Новые места берут эту пару.
  Нижний край каталога Data (§5.8 выше) остался на `mask-image` и переписывается
  отдельной правкой, а не этой историей: там за краем список, а не контрол, и
  цена ошибки другая.

## 6. Data & state conventions

### Enums (ровно как в REST-контракте, без proto-префиксов)
```ts
type UserStatus    = 'INVITED' | 'ACTIVE' | 'BLOCKED' | 'LOCKED';
type ProjectRole   = 'ADMIN' | 'MEMBER' | 'VIEWER';
type IssueType     = 'TASK' | 'BUG' | 'STORY';
type IssuePriority = 'LOW' | 'MEDIUM' | 'HIGH';
type IssueStatus   = 'TODO' | 'IN_PROGRESS' | 'DONE';
type IssueEventType =
  | 'CREATED' | 'TRANSITIONED' | 'ASSIGNED' | 'PRIORITY' | 'UPDATED' | 'DELETED'
  | 'COMMENT_CREATED' | 'COMMENT_UPDATED' | 'COMMENT_DELETED';
```
Комментарий (`IssueComment`): `id`, `issueId`, `projectId`, `authorUserId`, `body`,
`createdAt`, `updatedAt` (`null`, пока не редактировали — по нему и рисуется пометка
«edited»), `version`.
Отображаемые названия статусов: `TODO → "To Do"`, `IN_PROGRESS → "In Progress"`, `DONE → "Done"`.
Названия типов: `Task` / `Bug` / `Story`. Приоритеты: `Low` / `Medium` / `High`
(в узких сегментах — `Med`).

### Формат данных
- Идентификаторы — UUID-строки; в UI показываем `issueKey` (`ABC-123`), а не id.
- Время — ISO-8601 UTC; в UI: на карточке `MMM d` («Jun 25»), в мете/ленте `MMM d, HH:mm` (24ч),
  в уведомлениях — относительное («2h ago», «Yesterday»).
- Enum-значения не локализуем в данных, только при выводе.

### State layering
| Слой | Что | Где |
| --- | --- | --- |
| session | currentUser, accessToken/refresh | auth-контекст + `GET /users/me` |
| route | projectId, issueId | URL (§7 handoff README) |
| server | projects, membership, workflow, issues, issue+history, comments, notifications | react-query, мутации оптимистичные + инвалидация |
| board ui | `{ q, type, assignee }`, dragIssueId, dragOverStatus | локальный стейт экрана |
| app ui | theme, notifOpen, creating, draft, editingCommentId | локальный стейт / контекст, theme persist |

Правило: **никогда** не дублировать серверные данные в локальном стейте — только id и ui-флаги.

Исключение — черновики инлайн-редактирования (summary/description задачи, тело
комментария). Их приходится держать локально, потому что пользователь печатает быстрее,
чем отвечает сеть. Пересев с серверного значения делается **на рендере**, а не в
`useEffect`: эффект стоит лишний проход рендера на каждом рефетче, а сброс через `key`
сбивает фокус посреди набора текста. Для строки комментария `key` наоборот уместен — там
переключение в режим правки и должно пересоздавать черновик.

### Режимы API
`VITE_TASKA_API_MODE`: `mock` (полностью в памяти) · `rest` (только гейтвей) ·
`hybrid` (по умолчанию). Переключение — в `src/api/client.ts`, общий контракт —
`src/api/TaskaApi.ts`.

`hybrid` существует только потому, что `TAS-137` ещё не задеплоен: membership и список
участников синтезируются на клиенте из `GET /projects/{id}` и `GET /users/me`. Следствие
для UI — **в проекте виден ровно один участник**, текущий пользователь, независимо от
того, сколько их на самом деле. Фильтр по исполнителю и чипы assignee в этом режиме не
могут предложить никого другого.

Полный разбор — `docs/ai/API-DIVERGENCE.md`. Когда `TAS-137` выедет, `HybridTaskaApi`
удаляется целиком, а режим по умолчанию становится `rest`.

>   истории. Поднять на 44 **обе** — даёт 44/44 и снимает §7, но правкой одной
>   этой строки не обходится: тот же рецепт `.search-box` носят поле бара доски

>   бара пол **46**, и поле 44 внутри строки 46 оставляет по пикселю сверху и
>   снизу. То есть «поднять §4.14 на тач-ширинах» — это на самом деле правка и
>   §4.13, и §2.7. Второй выход — расширить область нажатия псевдоэлементом,
>   оставив обе окрашенные коробки на 32: §7 просит тач-**цель**, а не крашеную
>   высоту, так что этот путь не спорит ни с одним из трёх параграфов. Он и есть
>   ответ. Два условия, когда его будут делать: **обе** коробки, а не одна —
>   цель 44 у кнопки рядом с целью 32 у поля это тот же разрыв, только в
>   измерении, которого не видно; и просветы перемеряются на каждом новом месте
>   (на 390 у этой строки 16 сверху и 22 до первой карточки, вертикального
>   расширения ±6 хватает и ничего не перекрывает). Тем же приёмом закрывается
>   и записанный ниже разрыв §4.20.
> - Поле глобального поиска (§4.20) на тач-ширинах остаётся **32** по высоте (168×32
>   на 390, 98×32 на 320 — числа сдвинулись в TAS-185, когда бар принял
>   колокольчик): §4.14
>   фиксирует высоту поля на 32, а §7 требует 44 — и это настоящий конфликт двух
>   правил этого документа, той же природы, что уже записанный ниже «+» колонки на
>   22. Тот же блок `≤820`, который только что установил пол 44 для строк списка,
>   оставил их триггер на 32. Найдено `art-director` при переспросе TAS-179, и это
>   запись, которую **создала** эта правка, а не подобранная из чужого разбора: на
>   первом заходе список пополнили двумя пунктами, признание которых ничего не
>   стоило, и это тот же дефект списка, что и умение только сокращаться.
> - Неоткрываемое попадание в §4.20 помечено `aria-disabled`, но не несёт ни
>   одного признака из рецепта disabled в §4.1 — визуально это обычная строка
>   плюс пояснение 10.5 `--fg-3`. Против мока недостижимо (поиск и так ограничен
>   видимыми проектами), поэтому состояние отревьюено по коду, а не увидено.
> - Живые области `role="status"` в §4.20 монтируются и размонтируются вместе со
>   своим текстом, а не обновляются на месте. Сегодня читалки объявляют — это
>   измерено, — но устойчивый приём это одна постоянная область с меняющимся
>   текстом; область, появляющаяся одновременно со своим содержимым, зависит от
>   таймингов читалки.
> - Контрасты ниже порогов: status-pill по рецепту §4.5 — 1.91:1 для `TODO`;
>   неактивные сегмент-табы (`--fg-3` вместо `--fg-2` из §4.2) — 2.76:1;
>   тип-чип `Story` на подсвеченной строке §4.20 — **2.48:1 в светлой** (на
>   обычной строке 3.00, то есть ровно на пороге, и под порог его уводит любая
>   заливка). Оставлено сознательно, потому что тип несёт себя не цветом одним
>   (§2.2), — но записано, а не умолчано: §4.20 двумя пунктами выше опирается на
>   этот же порог 3:1, чтобы обосновать кольцо выделения.
> - Touch-таргеты на 390px меньше 44×44 (колоночный «+» — 22px; здесь §7
>   противоречит §4.9 — решить в доке при закрытии TAS-142).

- Контраст: основной текст ≥ 7:1, вторичный ≥ 4.5:1, `--fg-3` использовать только для
  некритичной меты (≥ 3:1). Проверять оба режима.
- **Как мерить контраст на подложке из `color-mix(… , transparent)`.** Считать по
  фактически отрисованным пикселям: взять вычисленное браузером
  `oklab(… / α)` и скомпоновать его над цепочкой родителей. Не «подмешивать»
  `transparent` к координатам вручную: CSS смешивает с `transparent`
  **premultiplied**, поэтому оттенок сохраняется целиком и падает только альфа,
  а ручное смешение уводит цвет к чёрному и меряет текст против плоскости
  *под* тинтом, а не против самого тинта.
  Ошибка не случайна и потому опасна: она **занижает на светлой теме (−12%) и
  завышает на тёмной (+11%)**. На 12% тинте это безобидно, но на рецепте
  статус-пилюли из §4.5 (16% тинт, семантический цвет текста на тёмной теме)
  тот же метод превратит непроходной коэффициент в проходной.
  Установлено `art-director` 2026-08-12 при сверке двух расчётов одного и того
  же баннера, разошедшихся на 1.8 пункта.
- Цвет никогда не единственный носитель смысла: тип — цвет + форма чипа + текст; приоритет —
  количество баров + `title`; статус — колонка + подпись.
- Focus-visible на всём интерактивном: `outline:2px solid var(--accent); outline-offset:2px`.
  **Одно исключение по знаку отступа, и оно обязательное** (TAS-185): строка во всю
  ширину внутри панели с `overflow:hidden` берёт `outline-offset:-2px`, потому что
  наружное кольцо панель срезает — замерено, при `+2px` у строки уведомления
  оставалась только верхняя грань из четырёх. Прецедент в коде старше правила:
  `.user-profile-admin` и `.user-profile-logout` рисуют так же и по той же причине.
  Записано именно как исключение, а не как вольность: без этой строки следующий
  ревьюер увидит `-2px`, назовёт нарушением и вернёт кольцо, у которого нет трёх
  сторон.
  **А строка, стоящая на углу самой панели, вдобавок берёт её внутреннюю дугу** —
  `calc(--pop-radius - 1px)`, тот же приём, что §4.20 применяет к панели поиска:
  без него у последней строки срезало два нижних угла на 4.97.
- Slide-over и модалка: `role="dialog"`, `aria-modal="true"`, focus trap, `Esc` закрывает,
  возврат фокуса на триггер.
- Поповер уведомлений: `aria-expanded` на триггере, счётчик непрочитанных в `aria-label`.
- Иконки-кнопки без текста — обязателен `aria-label`.
- Drag & drop дублируется кнопками переходов (клавиатурный путь).
- Мин. область нажатия 28×28 (плотный тулбар) / 32×32 (обычные), на тач-макетах — 44×44.
- Уважать `prefers-reduced-motion`.

## 8. Code conventions for UI

### Фактическая структура

Раздел описывает то, что есть в репозитории, а не то, к чему стоило бы прийти.
Если появляется новый файл — он встаёт в одну из этих папок.

```
src/
  screens/      App, LoginScreen, ProjectsScreen, BoardScreen — экраны и их состояние
  components/   переиспользуемые куски UI: Avatar, Modal, ThemeToggle,
                UserProfileMenu, TaskaLogo, IssueBits (type-chip, priority-bars)
  api/          TaskaApi (контракт) + mock/ · rest/ · HybridTaskaApi + client.ts
  domain/       types.ts — enum'ы и модели ровно по REST-контракту
  hooks/        useTheme
  lib/          format.ts — форматирование дат и семантические константы §2.2
  test/         setup.ts для vitest
  styles.css    один глобальный файл со всеми классами
```

Стили — **один глобальный `src/styles.css`** с плоскими именами классов
(`.issue-card`, `.comment-item`, `.board-column`). Не CSS Modules, не Tailwind,
не styled-components. Токены §2 объявлены на `:root` там же.

**Известный долг.** `BoardScreen.tsx` — около 1200 строк: доска, фильтр-бар,
slide-over задачи, тред комментариев, модалка создания и поповер уведомлений живут
в одном файле. Разносить по одному компоненту в файл имеет смысл при следующей
крупной правке доски; специально под это отдельную задачу пока не заводили.
Записано как долг, а не выдано за архитектуру.

- **Один компонент — один файл** для всего нового кода; имя файла = имя компонента.
- **Токены только через переменные.** Хардкод hex в компонентах запрещён, кроме семантических
  констант из §2.2 — они объявлены в одном месте, `src/lib/format.ts`
  (`statusColors`, `typeMeta`, `priorityMeta`).
- Тема — атрибут `data-theme` на `<html>`; не использовать классы `.dark` вперемешку с media-query.
- Не создавать вариант компонента ради одного отличия — прокидывать проп (`size`, `tone`, `variant`).
- Иконки — один набор (`lucide-react` или локальные inline-SVG), `stroke-width` 1.2–1.7,
  `currentColor`, размеры кратны шагу из §2.7. Не смешивать наборы.
- Списки: `key` = доменный id (`issue.id`), не индекс.
- Никаких инлайн-`!important`; специфичность решаем структурой.
- Числа-магии в вёрстке допустимы только из шкал §2.4/2.5/2.7.

Про `labelColor`. Цвет метки выбирает **пользователь**, а хранит и отдаёт его
**сервер** — это данные, а не токен, поэтому он и попадает в `style` инлайном
(§4.5). Здесь зафиксирован только набор, предлагаемый при создании метки. Семь
из восьми значений — это §2.2; первое, `#0052cc`, взято не на глаз, а из
контракта: `CreateProjectLabelRequestDto` даёт его примером (`Пример:#0052CC`)
в паре с именем `backend`, и этот же пример засеян в мок. Контракт по CLAUDE.md
стоит выше этого документа, так что расхождение с §2.2 здесь — не отклонение, а
подчинение.

**Контраст.** Набор наследует записанный в §7 пробел рецепта §4.5, и это надо
читать буквально: ни одно из восьми значений не проходит 4.5:1 в обеих темах
сразу. Замерено методом §7 (композит `oklab(… / α)` по цепочке родителей),
светлая / тёмная: `#0052cc` 5.26 / **2.46**, `#0ea5e9` 2.36 / 5.30, `#3fa863`
2.56 / 4.94, `#e3a008` **1.99** / 6.25, `#e5544b` 3.03 / 4.20, `#ec4899` 2.90 /
4.37, `#8b5cf6` 3.47 / 3.69, `#6366f1` 3.64 / 3.53. Значение по умолчанию в
тёмной теме не дотягивает даже до порога 3:1 для второстепенной меты.

Это не дефект набора и не повод его переподбирать: то же самое рецепт §4.5
делает с любым насыщенным цветом §2.2 — со статус-пиллами в том числе, для
которых §7 уже держит это за собой с ключом TAS-142 (замеренные там 1.91:1 у
`TODO`). Type-чипы сюда не входят: у них сплошная заливка без текста внутри
(§4.6), а рецепт «подложка плюс тот же цвет текстом» просто нечему там
испортить. Перекрашивать метки
в отрыве от рецепта означало бы чинить системную проблему в одном частном
месте. Имя метки поэтому всегда текст, а не только цвет (§4.6): читаемость
метки не должна зависеть от контраста её цвета.

Здесь это сказано прямым текстом по причине из преамбулы §7: этот документ не
должен читаться как описание состояния, которого у продукта нет. Фраза
«каждое значение читаемо в обеих темах» стояла тут до правки TAS-169 и была
неверна — она бы санкционировала следующий добавленный цвет.

**На бейдж ключа проекта это оправдание не распространяется** (TAS-171). Оно
держится на том, что имя метки всегда текст, а цвет стоит рядом со смыслом; у
ключа цвет был бы самим глифом, и «читаемость не зависит от контраста цвета»
там означало бы ровно обратное. Плюс цвет метки выбирает пользователь, а цвет
ключа выбирает сборка — свободный выбор, упавший ниже порога, это не
унаследованный долг, а новый дефект. Поэтому бейдж ключа берёт из набора только
тинт, а текст держит на `--fg-2` (§4.5), и в отличие от метки под TAS-142 он не
уходит.

Значение вне набора — легальный ответ сервера, и рисуется оно как есть, лишь
бы проходило контрактный `^#[0-9A-Fa-f]{6}$`; не прошедшее заменяется на
`--accent`, потому что нечитаемый чип хуже неточного (§4.5).

## 10. Definition of done для UI-задачи

1. Совпадает с прототипом по токенам §2 (цвета, типографика, отступы, радиусы, тени).
2. Работает в светлой и тёмной теме; контраст проверен в обеих.
3. Есть состояния: loading (скелетон), empty, error (тост с `requestId`), disabled, focus, hover.
4. Клавиатурная доступность: tab-порядок, focus-visible, `Esc` для оверлеев, альтернатива drag'у.
5. Права по роли (`VIEWER` — read-only) учтены в UI.
6. Мутации оптимистичные, с откатом и тостом при ошибке.
7. `prefers-reduced-motion` уважается; entrance-анимации не скрывают контент.
8. Нет хардкод-цветов и магических отступов вне шкал.
